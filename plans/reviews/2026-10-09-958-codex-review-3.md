## BLOCKER findings

### F1 — “One ask ever” is not implementable with post-then-persist

**Spec location:** §3 step 5; §4 “One ask ever”; §4 state-file design.

**Tree evidence:**

- Posting is an external operation: `bobi/auth_bootstrap.py:382-390`.
- Gateway posting is a separate HTTP request returning the remote ID: `bobi/events/gateway.py:61-80`.
- State persistence is a later local rename: `bobi/fsutil.py:100-139`.
- The gateway request has no idempotency key or caller-supplied message ID: `bobi/events/gateway.py:61-80`.

**What breaks:**

There is an unavoidable ambiguity between “Slack/Discord accepted the ask” and “the returned ID was persisted.” A process death in that window, or a timeout after the platform accepted the message, leaves a visible ask with no stored ID. The next boot sees no state and posts another ask.

`atomic_write_text` protects the local write; it cannot make the remote post and local write atomic. Verification item 15 starts with an already-stored ID and cannot catch this.

**Do instead:**

Add platform/gateway idempotency for the ask, using a durable caller-generated key. Recovery must be able to repeat the send and receive the same message ID. Add fault injection for:

1. Remote delivery succeeds.
2. The response is lost or the process dies before persistence.
3. Restart retries.
4. Exactly one visible ask exists.

Without that mechanism, D1 is not satisfied.

### F2 — The proposed catch-up primitive cannot support all transports promised by D5

**Spec location:** §3.2(d), “Discord and WhatsApp DMs stay supported”; §4 “One catch-up read”; verification items 4 and 15.

**Tree evidence:**

- `/channels/history` rejects adapters without `fetchConversation`: `event-server/core/src/core.ts:2433-2439`.
- The WhatsApp adapter implements send/upload only; it has no `fetchConversation`: `event-server/core/src/channels.ts:471-571`.
- Discord history reports `user` as username first, then ID: `event-server/core/src/channels.ts:612-628`.
- The proposed Slack identity source returns Slack identifiers only: `bobi/slack.py:302-323`.
- The history schema contains only `{user,text,ts,files}`: `event-server/core/src/channels.ts:119-124`.

**What breaks:**

- A WhatsApp restart with a reply in the gap cannot perform the promised catch-up at all; `/channels/history` returns an error.
- Discord cannot apply the stated “newest message whose `user` is the bot’s own user id” rule because history normally returns the bot username, while `require_app_identity` is Slack-only.
- Therefore the “one code path” and “DMs are supported with zero adapter changes” claims are false.

The synthetic history cases in verification item 15 can pass while the real WhatsApp endpoint rejects the call and Discord cannot establish its baseline.

**Do instead:**

Provide a transport-neutral catch-up contract that actually exists for every supported DM transport. It needs:

- Stable message identity/order.
- Stable author ID.
- Bot/human authorship.
- History for WhatsApp, likely backed by normalized inbound events stored by the event server because the current channel adapter has no history implementation.

This materially expands the event-server scope, but it is required to satisfy D1 and D5 together.

### F3 — Catch-up cannot prove that the triggering message was human

**Spec location:** §3.2(d) “Human-only”; §4 catch-up freshness rule; verification items 2 and 15.

**Tree evidence:**

- Live Slack events preserve `bot_id`: `event-server/core/src/adapters/chat-sdk-slack.ts:154-168`.
- Slack history discards `bot_id` and subtype: `event-server/core/src/channels.ts:280-295`.
- Discord history likewise discards `author.bot`: `event-server/core/src/channels.ts:612-628`.
- The exported history contract has no authorship field: `event-server/core/src/channels.ts:119-124`.

**What breaks:**

The live predicate can reject `fields.bot_id`; the catch-up predicate cannot. “Non-empty `user`” does not prove a human author. A third-party bot with a user identity can satisfy the restart catch-up and start the credential-minting flow, violating D5.

Verification item 2 tests only live events. Item 15 tests empty `user`, not a bot-authored history row with a non-empty user.

**Do instead:**

Extend `ConversationMessage` with an authoritative `author_id` and `is_bot`/`author_kind`, preserve those fields in each adapter, and apply exactly the same human-only rule in live and catch-up paths.

### F4 — Catch-up races the live queue and can submit “ready” as Claude’s OAuth code

**Spec location:** §3.2(c); §4 “after the listener is live … read … once”; verification items 1, 15, and 17.

**Tree evidence:**

- The live client queues every event immediately: `bobi/events/client.py:453-462`.
- History is a separate request: `bobi/events/gateway.py:96-102`.
- Claude’s current code extractor accepts any non-empty message and returns its last whitespace-delimited token: `bobi/auth_bootstrap.py:500-510`.

**What breaks:**

A ready reply arriving after the listener connects but before/during history fetch can appear in both places:

1. Catch-up history accepts it as “ready.”
2. The duplicate remains in the live queue.
3. Claude enters its pasted-code wait.
4. `_extract_code` consumes the duplicate and writes the last word of the ready reply into the PTY as the OAuth code.

The proposed ordering tests use a clean sequence and do not exercise this overlap.

**Do instead:**

Carry a consumed-message watermark or stable message ID from readiness into the pasted-code phase. The second wait must reject the ready event and anything not newer than it. Add a test where the same reply exists simultaneously in history and the live queue.

### F5 — Already-threaded Slack destinations produce an unsatisfiable channel predicate

**Spec location:** §3.2(b)-(d); §4 ask text; verification items 3-5.

**Tree evidence:**

- Conversation refs explicitly accept an existing thread trailer: `bobi/conversation.py:43-59`.
- Slack send uses the destination’s existing `threadId`: `event-server/core/src/channels.ts:332-340`.
- Inbound Slack replies carry the root thread timestamp: `event-server/core/src/adapters/chat-sdk-slack.ts:103-106`, `:160-166`.

**What breaks:**

If `BOBI_LOGIN_CHANNEL` is already `slack:...:channel:...:thread:<root>`, the ask is a reply inside that thread. Slack does not create nested threads. A human response still has `thread_ts=<root>`, never `thread_ts=<ask ts>`. The proposed predicate therefore waits until timeout forever.

A threaded DM ref also conflicts with D5’s “any human message in the DM” rule because the existing conversation filter matches only that thread.

**Do instead:**

Either reject every pre-threaded login destination up front, or define correlation against the pre-existing root plus a message boundary after the ask. Add explicit tests for threaded Slack channel and DM refs.

### F8 — “Failed post into a stored thread is treated as absent” contradicts “never re-post”

**Spec location:** §4 “Invalidated, not trusted”; §4 opening guarantee; verification item 16.

**Tree evidence:**

- Gateway send failures are surfaced as request exceptions: `bobi/events/gateway.py:29-59`.
- Transport failures after partial/actual delivery are possible: `event-server/core/src/core.ts:2346-2375`.

**What breaks:**

If “treated as absent” means clearing/ignoring the stored ask, the next boot posts a second ask, directly violating D1. A timeout can also be ambiguous: the thread post may have landed even though the client observed failure.

Verification item 16 explicitly pins this contradictory behavior.

**Do instead:**

A failure posting the URL/outcome into an existing ask must leave the ask state intact and fail the run. Reuse the same stored ask on restart. Permanent thread deletion needs an explicit human recovery action; it cannot silently authorize another ask under D1.

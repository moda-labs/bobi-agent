## Verdict

**NOT READY.**

The design shape is still right and round 1 already confirmed its one feasibility risk. The fold is also mostly good work: 11 of the 15 round-1 findings were folded correctly, and round 2 was right to overrule round 1 on F3 (I measured it: `codex` really does read `${CODEX_HOME}/auth.json`, so round 1's "leave `:547` on `${HOME}/.codex`" would have left an `api_key`-mode team with no codex credential at all).

It is not ready for three specific reasons, not because the design is wrong.
First, the fold left a reachable path to the exact silent symlink loop it was written to remove: the new 3b cleanup line sits inside `if [ -d /opt/bobi/skills ]`, and that directory is absent on any image whose team declares no build `run:` steps (**F1**). Verification item 12 as specified passes while that bug is present.
Second, the spec gates implementation on Q1 and Q4, and their recommended answers are refuted and mutually incompatible: `codex logout` deletes the file-level symlink Q4 rests on, and Q1's recommended Option C has nowhere to store the ask `ts` under Q4's shape (**F3**, **F4**).
Third, the new non-clobber guard pins a corrupt `auth.json` permanently and logs that it preserved an OAuth file (**F2**), recoverable only with the `fly ssh` access Z1 says cannot be assumed.

All five blocker/major fixes are small. None of them touches sections 1 to 3.3.

### F1 - blocker - The 3b cleanup line is inside the `/opt/bobi/skills` guard, so the silent symlink loop survives on any image without baked skills

**Claim (§3.4):** "and one line inside the codex-brain block, **before `:491`**, to drop a link a previous non-codex boot may have left on the volume". Presented as closing the loop hazard completely; the matrix lists the resulting shape as `OK` on all six boot orders.

**What I read.** `docker/docker-entrypoint.sh:489-491`:

```
489|   if [ -d /opt/bobi/skills ]; then
490|     log "Linking baked team skills into ${BRAIN_CRED_DIR}/skills for codex"
491|     mkdir -p "${BRAIN_CRED_DIR}/skills"
```

"Before `:491`" puts the cleanup line **inside** that `if`. And `/opt/bobi/skills` is conditional, which is exactly why `:394` and `:489` both guard for its absence. `bobi/build_render.py:213-220`:

```
213|     if spec.run:
220|             f"install -d -o {APP_USER} -g {APP_USER} {BAKED_SKILLS}",
```

A team that declares no build `run:` steps never gets `/opt/bobi/skills`.

**What I ran.** My own harness, with the real `:481-532` block extracted verbatim (`sed -n '481,532p'`), the spec's cleanup line patched in before `mkdir -p "${BRAIN_CRED_DIR}/skills"`, the spec's 3c appended, and a fresh `$HOME` per boot on one persisted `$DATA_DIR` (correct: `Dockerfile:288` is `VOLUME ["/data"]` only, so `/home/bobi` resets).

With `/opt/bobi/skills` present, I reproduce the spec's matrix exactly:

With `/opt/bobi/skills` absent, the loop is back:


### F2 - major - The new non-clobber guard pins a corrupt `auth.json` forever, in both auth modes, and logs that it preserved an OAuth file

**Claim (§3.4):** "`codex_auth_uses_api_key` (`:336-355`) exits 0 only for a file with a non-empty `OPENAI_API_KEY` and no `tokens`, and exits 1 for a missing or unparseable file, so the guard reads as 'a non-api-key file is present'."

The description of the predicate is accurate. The consequence for an unparseable file is not stated, and it is the one state with no recovery.

**What I read.** `docker/docker-entrypoint.sh:344-347`, inside `codex_auth_uses_api_key`:

```
344| try:
345|     data = json.loads((Path(os.environ["CODEX_CRED_DIR"]) / "auth.json").read_text())
346| except Exception:
347|     sys.exit(1)
```

And the writer that can produce the corrupt state, `:330`, is a plain non-atomic write:

```
330| path.write_text(json.dumps({"OPENAI_API_KEY": os.environ["OPENAI_API_KEY"]}) + "\n")
```

**What I ran.** The spec's proposed guard and the `:553-563` sweep, both driving the real `materialize_codex_api_key_auth` and `codex_auth_uses_api_key` extracted verbatim (`eval "$(sed -n '319,355p' docker/docker-entrypoint.sh)"`):

```
=== BOBI_AUTH=api_key, OPENAI_API_KEY set ===
    [ep] Writing Codex API-key auth file from OPENAI_API_KEY
  absent   api_key   before=(none)                    after={"OPENAI_API_KEY": "sk-AMBIENT-ENV-KEY"}
    [ep] Leaving durable Codex OAuth auth file intact; not materializing OPENAI_API_KEY
  oauth    api_key   before={...,"tokens":{...}}      after={...,"tokens":{...}}
    [ep] Writing Codex API-key auth file from OPENAI_API_KEY
  apikey   api_key   before={"auth_mode":"apikey",…}  after={"OPENAI_API_KEY": "sk-AMBIENT-ENV-KEY"}
    [ep] Leaving durable Codex OAuth auth file intact; not materializing OPENAI_API_KEY
  garbage  api_key   before={"OPENAI_API_KEY":"sk-tr  after={"OPENAI_API_KEY":"sk-tr
=== BOBI_AUTH=subscription (the sweep arm) ===
  oauth    subscription  preserved
  apikey   subscription  removed
  garbage  subscription  PRESERVED
```

Absent, OAuth and api-key are all handled correctly, so the guard does fix F3. A truncated file is preserved by the guard **and** by the subscription sweep, so neither auth mode can clear it. And what codex does with it:

```
$ CODEX_HOME=.../garb codex login status
Error checking login status: EOF while parsing a string at line 1 column 24
  rc=0
```

So: codex is broken, the entrypoint logs "Leaving durable Codex OAuth auth file intact", and the only recovery is `rm` over a shell, which Z1 removes from the assumption set. Root-owned is fine (the guard and the predicate both run as root in section 3).

**Fix.** Make the predicate's intent explicit instead of inferring it by negation. Either add a `codex_auth_is_oauth` helper (`parses AND data.get("tokens")`) and guard on that, or guard on `codex_auth_uses_api_key || ! <parses>`. Then add the garbage leg to verification item 11, which currently specifies only the OAuth and api-key states.

### F3 - major - Q4's recommendation is refuted by `codex logout`: it deletes the symlink, so logout is not durable and the next boot revives the logged-out credential

**Claim (§5, Q4):** "Writes are in place. The symlink survives both. ... **Recommendation: take the file-level symlink.**"

I reproduced every measurement the spec lists, with the baked `codex-cli 0.144.5`. All three hold:

```
# write over a symlink whose target exists
Successfully logged in
  link still a symlink? YES
  vol content: {"auth_mode":"apikey","OPENAI_API_KEY":"sk-test-EXISTING-TARGET"}
# write through a DANGLING symlink
  pre: dangling? YES
Successfully logged in
  link still a symlink? YES
  vol/auth.json: '.../q4b/vol/auth.json' 600
# read through a dangling symlink
Not logged in
  rc=0
```

The spec did not test the unlink paths. `codex logout` does unlink:

```
### Q4 (d): does 'codex logout' unlink the symlink?
  before logout: link=YES vol_exists=YES
Successfully logged out
  after  logout: link=NO - LINK GONE vol_exists=YES
```

Full sequence with the real binary, simulating logout, re-login, and a reboot that re-runs the proposed `ln -sfnT`:

```
  1. after login:  vol={"auth_mode":"apikey","OPENAI_API_KEY":"sk-GENUINE-HUMAN-LOG
  2. after logout: link=GONE  vol={"auth_mode":"apikey","OPENAI_API_KEY":"sk-GENUINE-HUMAN-LOG
  3. re-login:     overlay file is REAL? YES-EPHEMERAL
                   overlay={"auth_mode":"apikey","OPENAI_API_KEY":"sk-RELOGIN-AFTER-LOG
                   vol    ={"auth_mode":"apikey","OPENAI_API_KEY":"sk-GENUINE-HUMAN-LOG
  4. after reboot: Logged in using an API key - sk-GENUI***LOGIN with key=sk-GENUINE-HUMAN-LOGIN
```

Two defects, neither listed in Q4:

- **Revocation is undone by a reboot.** The volume keeps the credential the human logged out of, the sweep at `:553-563` leaves an OAuth file alone, and the next boot's unconditional `ln -sfnT` re-exposes it. Confirmed on the Python side too, from `/tmp/wt-r2-main`: after the link is removed, `credentials_exist()` is `False`, so `run_bootstrap`'s `:630-633` short-circuit does not fire and a fresh login is attempted into the overlay.
- **A post-logout re-login is not durable.** It lands on `$HOME/.codex/auth.json` as a real file, lost on the next roll, and silently replaced by the stale volume credential.

Under the directory shape neither happens: `codex logout` deletes the real file on the volume, and a re-login writes the real file on the volume. The directory shape is strictly safer on this axis.

Q4's other three "what it does not simplify" items check out. I confirmed the `chown -R` one specifically, since it is the subtlest:

```
$ chown -Rv bobi:bobi .../co2/ch
  ownership of '.../co2/ch/auth.json' retained as bobi:bobi
  ownership of '.../co2/ch' retained as bobi:bobi
  target ctime UNCHANGED  -> chown never touched the target
$ chown --help | grep -- '-P'
  -P  do not traverse any symbolic links      (-P is the default)
```

**Fix.** Either keep the directory shape (3.4, which I otherwise found correct once F1 is fixed), or keep Q4 and add to it: a `codex logout` on a non-codex brain must also remove `${DATA_DIR}/codex/auth.json`, and the boot-time `ln -sfnT` must not re-expose a credential whose link was deliberately removed. That is more machinery than the directory shape costs, which inverts Q4's own simplicity argument. I recommend the directory shape.

(Checked and **not** a finding: the self-referential case. With the `!= codex` gate bypassed on a codex brain, GNU `ln` refuses with `'...' and '...' are the same file`, `rc=1`, and the credential is intact. Under errexit that is a loud boot abort, not credential loss.)

### F4 - major - Q1's recommended Option C and Q4's recommended shape cannot both be implemented: C's storage location does not exist under Q4

**Claim (§5, Q1 Option C):** "It needs somewhere to remember the ask's `ts` across boots, and the durable volume the rest of this spec already introduces is that place (`${CODEX_HOME}` for a tool, the brain credential dir for the brain)."

**Claim (§5, Q4):** "The alternative moves only the **file**, with **no env var at all**."

The spec recommends C **and** recommends Q4's file-level shape. Under the file-level shape `CODEX_HOME` is never exported, so `${CODEX_HOME}` is unset and C's named storage location does not exist. §8 says implementation must not start "before Q1 and Q4 are answered", and the two recommended answers conflict.

`${DATA_DIR}/codex` does still exist under Q4 (its snippet `mkdir -p`s it), so the repair is one word. But as written, an implementer following both recommendations has no location, and Option C is the one option the spec says costs more than "one `if target is None`" precisely because of this persistence step.

**Fix.** Name `${DATA_DIR}/codex` rather than `${CODEX_HOME}` in Q1-C, and state that the persisted `ts` must be cleared once the login succeeds, so a later re-login does not revive a months-old thread.

### F9 - minor - The errexit claim is stated as a general property of AND lists and is not one

**Claim (§3.4):** "The bare `[ -L ... ] && rm -f ...` form is safe under `set -euo pipefail`: ... where a failing non-final command of an AND list does not trigger the errexit."

The conclusion is right for the stated placement; the rule is not. bash exempts the AND-list's non-final command, but the list's own status still propagates from some syntactic positions.

```
A: standalone, path absent
A: reached next line rc=1
B: mid-block, path absent
B: reached next line rc=1
B: mkdir after the guard ran
C: LAST command of a function
=== script exit: 1 ===
```

As the last command of a function body it aborts. Mid-block, which is where the spec puts it, it is safe. Replayed in the spec's exact shape (inside the codex `if`, inside the `[ -d ]` `if`, immediately before `mkdir -p "${BRAIN_CRED_DIR}/skills"`): `SURVIVED to end`, `exit: 0`.

**Fix.** Say "safe in this position (not the last command of a list or function body)".

### F13 - minor - The non-clobber guard is added only to the non-codex arm, so §6's claim is false on a codex-brained `api_key` team

**Claim (§6, Accepted and stated):** "the non-clobber guard in 3.4 keeps it that way across boots."

The guard replaces `:546-548`, the non-codex arm.

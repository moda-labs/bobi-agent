### R4-F3 (major): "round 3 did not reproduce the PATH-alias helper binaries" is an artifact of measuring under `/tmp`

**The claim.** Spec line 629: "Round 2's wording here claimed codex writes 'PATH-alias helper binaries'; round 3 did not reproduce that (its R3-F12). The measured footprint is above, and it contains no `bin` directory."

**Measured, with `CODEX_HOME` outside `/tmp`.** `CODEX_HOME=$HOME/r4-codexprobe codex login status`, then `codex exec`:

```
$CH/tmp/arg0/codex-arg0Vd7mrE/apply_patch            -> /usr/local/bin/codex
```

Four PATH-alias helper entries, created inside `CODEX_HOME` on *every* invocation (a fresh `codex-arg0*` dir per run; the previous one is removed, so there is no unbounded leak).

**Why round 3 saw none.** With `CODEX_HOME` under `/tmp`, codex 0.144.5 refuses:

```
WARNING: proceeding, even though we could not create PATH aliases: Refusing to create
helper binaries under temporary dir "/tmp" (codex_home: AbsolutePathBuf("/tmp/.../there"))
```

Round 3's sandboxes were all `mktemp -d` under `/tmp`, so its negative result is a property of the test location, not of codex. "No `bin` directory" is literally true and irrelevant: the directory is `tmp/arg0/codex-arg0*`.

**The repo documents the behaviour and the incident it caused.** `tests/integration/test_container_image.py:277-284`:

> "a root-run step that writes to $HOME (the codex --version smoke did this: codex drops PATH-alias helpers under ~/.codex on any invocation) bakes a root-owned dir into the agent HOME. ... the gstack `--host auto` bake died on root-owned /home/bobi/.codex exactly this way at the 0.47.0 fleet roll."

### R4-F4 (minor): `as_app` drops the privilege the predicate it replaces had, and flips the failure direction on an unreadable credential

**The change.** Spec lines 370 and 401 both call the validator through `as_app` (`docker/docker-entrypoint.sh:414-420`), which is `gosu "${APP_USER}" env ...`. The predicate it replaces, `codex_auth_uses_api_key` (`:336-355`), is called inline at `:559` and therefore runs as **root**.

**Measured.** A valid OAuth `auth.json` the calling user cannot read:

```
credential-status codex <chmod-000 valid oauth file>  ->  rc=1
   credentials invalid: credential file is unreadable
[ -f <same file> ]                                    ->  true
```

`subscription_credentials_status` maps `OSError` to invalid at `bobi/auth_bootstrap.py:136-137`, so "cannot read" and "not a usable credential" become the same answer.

**Both arms go the wrong way.** A root-owned mode-600 `/data/codex/auth.json` holding a real OAuth credential:

- `api_key` mode: the guard's `if` is false, so `materialize_codex_api_key_auth "${CODEX_HOME}"` overwrites it.
- subscription mode: `[ -f ]` is true (root can stat) and `! credential-status` is true, so the sweep deletes it, every boot.

Those are the two failures the guard and the sweep exist to prevent.

**Reachability.** No entrypoint path produces a root-owned `auth.json`: `materialize_codex_api_key_auth` ends with `chown -R` (`:333`), `login-bootstrap` and `codex login` run via `as_app`, and the first-boot `chown -R "${DATA_DIR}"` (`:372`) chowns toward `bobi`. The plausible route is an operator following the fallback the code itself prints (`bobi/auth_bootstrap.py:719`, "`fly ssh console` then `codex login --device-auth`") who knows to set `CODEX_HOME=/data/codex` in that root shell. Unobserved, which is why this is a minor and not a major.

**Fix.** One line before the check, which also closes the gap that 3c chowns the directory but never the file:

```sh
chown "${APP_USER}:${APP_USER}" "${CODEX_HOME}/auth.json" 2>/dev/null || true
```

Dropping `as_app` would also work and would preserve the old privilege exactly, but only if the wheel is importable by root in the image, which I could not verify here.

## VERDICT

The spec is not ready for Gate 1. The first required change is to define a rich internal observation separate from the public `{error, since}` heartbeat block. As written, Shape R cannot drive its own alert state machine without either an undocumented payload or a second registry scan that violates the one-observation guarantee.

## Findings

### F1 - The specified `session_health` value cannot drive the specified alerter

Severity: **BLOCKING**

Evidence:

- Shape R gives `SupervisorState.session_health` only `null` or `{error, since}` (spec branch, `docs/specs/992-session-fatal-probe-edge.md:282-313`), and the data-flow diagram passes that same block to both consumers (`:390-409`).
- The alerter also needs the normalized signature, affected session names, successes with `started_at`, and whether `null` means “condition false” or “registry read failed” (`:664-694`).
- The current fold says an exception-path null behaves differently from a computed null (`:681-684`), but both have the same representation. This is an incomplete fold of round 4 J10, which requested that distinction (spec branch, `plans/reviews/2026-10-09-992-review-4.md:257-260`).
- A second alerter scan would violate the explicit one-read guarantee (`docs/specs/992-session-fatal-probe-edge.md:645-654`).
- Current main’s `CompositeObserver` only forwards one unchanged `SupervisorState`; it does not provide an enrichment channel (main-70db2e10, `bobi/supervisor/supervision.py:194-209`).

What I would change:

Define an internal `SessionHealthObservation` containing at least `read_ok`, `condition`, normalized signature, raw error, `since`, affected names, and relevant success entries. Attach that once to `SupervisorState`. Let `snapshot.py` project it to public `{error, since}` while the alerter consumes the full observation. Add tests asserting one registry scan and distinguishing computed-null from read-failure.

### F2 - The manager-alive guard is placed before the authoritative manager verdict exists

Severity: **MAJOR**

Evidence:

- The condition claims `down` and `wedged` managers are excluded (`spec branch, docs/specs/992-session-fatal-probe-edge.md:458-469`), and test 7 supplies those values (`:955-959`).
- The design populates `session_health` in `Supervisor._report` (`:862-863`).
- On current main, `_report` has only the raw `/health` payload and does not derive the outside verdict (main-70db2e10, `bobi/supervisor/supervision.py:781-795`).
- The authoritative `running`/`idle`/`wedged`/`down` verdict is computed later inside `Telemetry._publish_heartbeat` (main-70db2e10, `bobi/supervisor/telemetry.py:127-162`).
- A raw manager can report `running` while `status_file_age` makes the outside verdict `wedged` (main-70db2e10, `bobi/supervisor/probe.py:109-122`). Thus the detector can publish a failure block and open Slack while the same heartbeat says the manager is wedged.

What I would change:

Compute the outside manager verdict once before session detection and carry it on `SupervisorState` for both telemetry and the detector. Add an integration case where raw status is `running`, status-file age makes the derived verdict `wedged`, and session-fatal remains null.

### F3 - Any unrelated success can falsely recover a scoped failure

Severity: **MAJOR**

Evidence:

- The spec claims coverage for scoped causes such as a bad model pin or gateway misconfiguration (spec branch, `docs/specs/992-session-fatal-probe-edge.md:69-73`).
- It also accepts repeated missing-workflow failures as valid incidents (`:594-601`).
- Recovery nevertheless accepts the first success from any session started after `opened_at` (`:670-672`, `:696-705`).
- Registry entries have `role`, `run_key`, `model`, and `provider` fields (main-70db2e10, `bobi/sdk.py:282-293`), but startup records do not reliably populate model/provider before a connect failure (main-70db2e10, `bobi/subagent.py:1506-1515`; `bobi/workflow/orchestrator.py:321-332`).
- The existing brain-availability mechanism avoids this error by keying incidents and recovery to an account boundary (main-70db2e10, `bobi/brain_availability.py:125-128`, `:165-176`).

A healthy session on model B can therefore post RECOVERED while model A’s bad pin continues failing.

What I would change:

Define the incident boundary explicitly. Recovery should match the affected provider/model/role/workflow boundary, or generic outcome incidents should use ABANDON rather than claim recovery. Add a test where an unrelated post-open success does not close the incident.

### F4 - N=3 within one hour is not supported by the measurements and misses sparse outages

Severity: **MAJOR**

Evidence:

- The only additional N=2 open is the two-session deadline pair (`spec branch, docs/specs/992-session-fatal-probe-edge.md:194-205`).
- The spec separately calls that pair a genuine deadline expiry and says such an expiry is a correct alert (`:154-160`).
- It nevertheless uses that correct fire as the argument for rejecting N=2 (`:204-205`, `:549-551`).
- The measured mean is only 0.47 dispatches per hour (`:639-643`), and 82% of hourly windows contain no terminal events (`:716-718`).
- The limitations name zero dispatches but not one or two failures per hour indefinitely (`:740-745`).
- Test 1 uses the unusually dense 13-failure incident; no test covers a persistent sparse outage (`:937-942`).

What I would change:

State sparse dispatch blindness explicitly and re-evaluate the rule. A simpler alternative is “the newest failure is fresh, and the last N terminal outcomes since the last success share a signature,” which does not require all N to fit inside one hour. If N=3 remains, characterize N=2’s extra alert as an accepted noise-policy tradeoff, not a measured false positive.

### F5 - Verbatim Slack errors bypass the existing secret-redaction boundary

Severity: **MAJOR**

Evidence:

- The spec requires the complete error verbatim in the block and Slack notice (spec branch, `docs/specs/992-session-fatal-probe-edge.md:307-309`, `:545-547`, `:664-666`).
- Connect-time exceptions are persisted through `tool_crash_error`, which embeds `str(exception)` without redaction or a length bound (main-70db2e10, `bobi/brain/turns.py:44-48`; `bobi/subagent.py:550-554`).
- The existing brain-availability path deliberately collapses whitespace, truncates to 500 characters, and redacts credential-shaped values before publishing externally (main-70db2e10, `bobi/brain_availability.py:68-74`, `:140-158`).
- None of the 19 planned tests covers redaction or message size (spec branch, `docs/specs/992-session-fatal-probe-edge.md:935-1022`).

What I would change:

Keep the raw error in the local registry, but pass Slack text through a shared bounded redaction helper. Add tests for `token=...`, `authorization=...`, and oversized multi-line exceptions.

### F6 - `done` cannot behave as the promised success under the proposed timestamp rule

Severity: **MINOR**

Evidence:

- The detector windows and orders terminal outcomes exclusively by `terminal_at` (`spec branch, `docs/specs/992-session-fatal-probe-edge.md:555-580`, `:624-625`).
- The spec nevertheless says `done` breaks streaks and closes incidents, and parametrizes tests 3 and 14 over it (`:574-580`, `:945-946`, `:989-991`).
- Current main’s real `mark_done` writer sets only `status="done"` and `pid=0`; it does not set `terminal_at` (main-70db2e10, `bobi/sdk.py:541-542`).
- `terminal_at` defaults to `0.0` (main-70db2e10, `bobi/sdk.py:319-320`).

A synthetic `done` fixture with a fabricated `terminal_at` can make both tests pass while the real writer remains invisible.

What I would change:

Either remove `done` from live success semantics, define and justify a `last_activity` fallback for legacy `done`, or change `mark_done` to stamp a terminal time while addressing historical entries. Tests should create the entry through the real writer.

### Q1 - Generic backstop or reported outage?

If the goal is specifically auth/quota/session-limit silence, there is a fourth, smaller shape: extend `brain_availability.py` to observe connect exceptions, add a distinct session-limit incident category, and route its existing events to an operator.

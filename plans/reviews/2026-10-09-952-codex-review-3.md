## Findings

### 1. Server eviction is an unmodeled fifth writer — blocker

**Spec claim:** `spec.md:235-247` says exactly four writers mutate S5. I5 (`:187-189`), L1/L5 (`:517-522`), and recovery (`:660-665`) assume the next manager start can PUT to the retained deployment.

**Code evidence:** both server implementations delete disconnected deployments. The local server sets a 60-second threshold:

`main-source/event-server/src/local.ts:71-78`

> “a deployment with zero WebSocket connections … will be removed”  
> `EVICTION_STALE_MS ... "60000"`

The sweep removes both index entries and the deployment:

`main-source/event-server/src/local.ts:825-847`

> `await storage.removeSubscription(...)`  
> `await storage.removeDeployment(...)`

The Worker performs the same deletion at `event-server/worker/src/deployment-session.ts:245-286`.

Meanwhile, a failed PUT to the stale identity deliberately does not re-register:

`main-source/bobi/subagent.py:1901-1924`

> `status in (401, 403)`  
> “saved deployment and completion cursor retained; retry pending”  
> `raise RuntimeError(message)`

There is already an integration test proving eviction: `tests/integration/test_inbox_transport.py:291-323`.

**Why it matters:** after a manager has been stopped for over 60 seconds, S5 and its remote identity are deleted while the local deployment record and S4 remain. The next non-fresh start chooses W2, receives 403, retains the stale credential, and retries the same unusable identity. Therefore:

- I5 is false as written.
- L1’s “takes effect at the next start” is not guaranteed.
- L5’s “the server keeps it” is false after eviction.
- Restart is not an unconditional D9 recovery.
- The source-of-truth list is missing the local deployment identity, and the writer list is missing eviction.

**Change:** model the deployment credential as distributed state and eviction as W5, add the eviction crash/staleness boundary, specify 403 recovery, and add an eviction-then-start integration test.

### 2. Concurrent CLI edits cannot satisfy test 5 or preserve both deltas — blocker

**Spec claim:** CLI step 5 serializes S2 (`spec.md:491-493`), then step 6 claims `accepted − removed + added` (`:495-497`). The accepted API accepts a fully computed list (`:443-444`). Test 5 expects concurrent adds to leave both topics in S2, S4, and S5 (`:703-704`).

**Code evidence:** `file_lock` locks a companion specific to the target path:

`main-source/bobi/fsutil.py:165-172`

> “The lock is taken on a companion `<name>.lock` file”  
> “only the lock keeps a concurrent updater's change from being overwritten.”

Thus the workspace-file lock and accepted-record lock are different locks. Nothing serializes the complete S2-edit/S4-claim transition.

**Why it matters:** two commands can both read old S4 `A`; one records S2 delta `+X`, the other `+Y`. They then claim `A+X` and `A+Y`. Generation CAS selects one claim but never forms `A+X+Y`.

Re-running the loser does not repair it: its topic is already in S2, so its “exact S2 delta” is empty and step 6 replays the incomplete S4 unchanged. The proposed test’s final assertion is therefore not implementable from the specified protocol.

**Change:** make the accepted-record operation an atomic delta transform—e.g. `claim_delta(added, removed)` reads and mutates current S4 while holding its lock—or use one local transaction lock covering the S2 write and S4 claim. Add a deterministic barrier where both commands read the same initial S4.

### 3. The CLI-versus-boot race remains open — blocker

**Spec claim:** `spec.md:303-306` says a writer cannot revert an already-live change and, for W4 concurrency, both candidate sets contain the operator change. I5 says every start reconciles S2 and S3.

**Code evidence:** boot snapshots subscriptions before publishing liveness:

`main-source/bobi/service.py:628-657`

> `subscribe = discover_subscriptions(project_path)`  
> …  
> `atomic_write_text(pid_path, pid_str)`

The already-captured list is passed to the session later:

`main-source/bobi/service.py:758-765`

> `run_persistent_agent(... subscribe=subscribe)`

The CLI’s proposed liveness check becomes true solely from that PID:

`main-source/bobi/service.py:842-847`

> `manager_running = bool(pid and _pid_alive(pid))`

**Why it matters:** an old accepted record can exist while a new boot has written its PID but has not completed W2:

1. Boot snapshots old S2 as `A`.
2. Boot writes its PID.
3. CLI sees L4, writes S2 `A+T`, and claims `A+T`.
4. W2 claims its stale boot snapshot `A` with a newer generation.
5. W2 can PUT `A` after the CLI PUT.

The stale boot writer does not contain the operator change, directly contradicting `spec.md:306`. Generation orders claims; it does not establish freshness. The test plan has no barrier covering this interval.

**Change:** make L4 require a current-boot readiness/epoch recorded only after W1/W2 confirmation, or have boot validate/reload the current S2 generation before claiming. Add a deterministic CLI-versus-W2 test between PID publication and boot claim.

### 4. Proceeding without the file lock invalidates the generation CAS — blocker

**Spec claim:** on timeout, W1/W2/W3 proceed without the lock and “the generation check still detects a lost update” (`spec.md:282-286`).

**Code evidence:** the current lock is explicitly advisory:

`main-source/bobi/fsutil.py:163-172`

> “Advisory, so it only serializes writers that also take it.”

**Why it matters:** suppose W4 holds the lock and has read generation `g`, then pauses. A boot writer times out, reads `g` without the lock, and writes `g+1`. W4 resumes and also writes `g+1`. Both confirmations now see their expected generation, so neither detects that the other reused it. The counter is no longer a CAS token.

The proposed bounded-lock test only proves startup does not block; it does not test the duplicate-generation interleaving.

**Change:** no code path may mutate S4 without acquiring its lock. On manager timeout, it may continue its network operation without updating S4, leave reconciliation pending, or fail/retry startup—but it cannot issue an unlocked generation. Test a holder paused specifically between reading `g` and writing `g+1`.

### 5. Computed ownership is not stable when monitors change — blocker

**Spec claim:** I1 requires S2 and S3 to remain disjoint (`spec.md:170-172`). `add T` accepts a topic not currently in D, while `remove T` rejects a topic currently in D (`:216-230`).

**Code evidence:** monitors can introduce an arbitrary event after that declaration:

`main-source/bobi/cli.py:3089-3099`

> `event=event or f"monitor/{slug}"`

The current effective monitor set is mutable:

`main-source/bobi/monitors/registry.py:120-124`

> `return result`

Boot converts those events into derived keys:

`main-source/bobi/service.py:636-647`

> `monitor_subscription_keys(monitor_events)`  
> `subscribe.append(key)`

**Why it matters:** an operator may legitimately add `support.email` while no such monitor exists. Later, adding `monitor/support.email` makes bare `support.email` derived. S2 and S3 now overlap, violating I1 without any subscription command.

The CLI then refuses to remove `support.email` because it is currently derived. If the monitor is later paused or removed, the stale S2 declaration keeps the topic subscribed.

**Change:** specify temporal ownership. Either permit overlap and define `remove` as removing the S2 declaration without dropping a currently derived S5 key, or make monitor mutations migrate S2 under a coordinated protocol. Add a declared → monitor-derived → declaration-remove → monitor-pause test.

### 6. The S2 writer model contradicts the supported hand-edit path — major

**Spec claim:** S2 is “written only by the CLI” (`spec.md:159`), yet the design explicitly discusses “a hand-edited S2” (`:227`) and builds a strict validator for hand-edit failures (`:375-388`).

**Code evidence:** only the package is protected read-only:

`main-source/bobi/runtime_guard.py:143-153`

> `package = paths.package_dir(runtime_root)`  
> `kind="team-package"`

The workspace is exposed as agent-owned domain content:

`main-source/bobi/prompts/resolver.py:86-96`

> “`workspace` holds domain files and work products.”

**Why it matters:** a human or agent can write S2 without using the advisory lock. Such a write can race the CLI’s read-modify-write and be silently overwritten. It is also absent from the writer and crash/interleaving tables.

**Change:** distinguish “supported writer” from “possible writer,” model manual/agent edits as an external S2 writer, and state the concurrency consequence and recovery. If direct editing is unsupported, say so explicitly in the file header and docs.

### 7. CLI arguments can create a file invalid under its own validator — major

**Spec claim:** every stored item must be a non-empty string after stripping (`spec.md:382`), but CLI step 2 only requires ownership validation (`:482-484`).

**Code evidence:** registration validates every element:

`main-source/event-server/core/src/core.ts:1397-1400`

> `subscriptions.every((s) => typeof s === "string" && s.length > 0)`

The update path does not:

`main-source/event-server/core/src/core.ts:1496-1518`

> `const replaceSubs = body.replace as string[]`  
> `if (replaceSubs !== undefined && !replaceSubs.length)`  
> `const desired = [...new Set(replaceSubs)]`

**Why it matters:** `subscriptions add ''` or a whitespace-only argument can be written to S2 and may reach the update endpoint. The next strict workspace read then rejects the CLI-created file and prevents manager boot. The server’s replace path does not provide a safety net.

**Change:** normalize and validate all CLI topic arguments—strip, reject empty, and reject duplicates as appropriate—before any write or network call. Add empty and whitespace argument tests.

## Genuine new design fork

### Recovery from an evicted or otherwise 403 deployment

The owner must choose between:

- automatically discarding the stale deployment identity, minting/registering a new deployment, and accepting loss of the old deployment’s replay sequence; or
- preserving today’s replay-safety stance and requiring an explicit destructive recovery such as `restart --fresh`, while weakening I5/L1 and documenting that operator action.

The current spec assumes automatic convergence but current code deliberately preserves the stale credential, so it cannot be handed to an implementer without this decision.

## 2. Findings

### F1 - BLOCKER - the restart grace does not close the restart-reap false positive

**Location:** §6.2, lines 473-478 (the stated condition) and 486-495 (the guard's justification); §3.2 line 223; §11 test 10, line 869.

**Claim:** "AND no manager restart occurred within the restart grace (300s, a constant)", and §3.2: "with the restart grace enabled it opens only on §3."

The grace is stated as a predicate on **evaluation time** ("no restart occurred within the last 300 s"), while the orphaned entries it is meant to exclude stay in the **3600 s lookback**.
At restart + 301 s the grace no longer suppresses and the same stale reaped entries satisfy the streak.
The guard buys 300 s of silence inside a 55-minute exposure window.

Command and output (the simulation applies the §6.2 condition verbatim at a 30 s poll cadence, over §3.1's real cluster):

```
$ PYTHONPATH=.../1008r2-main python3 - <<'PY'   # (full script in §4, item 10)
reap cluster size: 5
    2026-08-03 21:09:09 wf-issue-lifecycle-eng-team-858
    2026-08-03 21:09:09 wf-issue-lifecycle-eng-team-851
    2026-08-03 21:09:10 wf-pr-closed-eng-team-adhoc-fa0b931d
    2026-08-03 21:09:16 wf-issue-lifecycle-eng-team-884
    2026-08-03 21:09:19 wf-issue-lifecycle-eng-team-850

restart proxy instant: 2026-08-03 21:09:09  grace expires: 2026-08-03 21:14:09
reaped entries leave the 1h lookback at: 2026-08-03 22:09:19

Polling every 30s, condition AS WRITTEN in 6.2:
  FIRST OPEN at 2026-08-03 21:14:09 = restart+300s, i.e. 0.0 min after the grace expires
    entries: ['wf-pr-closed-eng-team-adhoc-fa0b931d', 'wf-issue-lifecycle-eng-team-884', 'wf-issue-lifecycle-eng-team-850']
    signature: 'agent process died without reporting a terminal status'
```

Test 10 as written ("N sessions reaped `crashed` **right after** a `manager_restarted` -> no edge") passes under this bug.
A test that advances the clock past the grace and re-polls would fail.

**What should change:** the guard must be a predicate on the **entries**, not on the evaluation time: discard any terminal entry whose `terminal_at` falls inside `[last_restart_at, last_restart_at + grace]` (or, equivalently, inside the same window as a `manager_restarted` edge), for as long as that entry is inside the lookback.
Then add the missing regression test: same fixture, poll at grace+1 and assert still no edge.
`SupervisorState.last_restart_at` already exists (`supervision.py:157`), so the input needs no new wiring - see F18.

### F2 - MAJOR - a `failing` incident has no path to close if dispatches stop, and the two consumers desync

**Location:** §6 state machine, lines 440-450; §7.1 CLOSE rule, line 665; §7.1 "Limitation", lines 681-686.

The only close transition is "the first session that both started after the incident opened and reached `completed`".
Nothing closes an incident when dispatch stops - which is the normal operator response to the alert ("act on the error above"), and the normal state of a low-traffic deployment.
The spec never states this.

Worse, the detector and the alerter then disagree, which is the exact failure §6.4's single-flight was introduced to prevent:

- At t=0 three failures land. Detector says `failing`, alerter opens, posts.
- At t > 1 h those failures age out of the lookback. The detector has no recent terminals, so by §6's own diagram it returns `unknown`, and the heartbeat publishes `session_health.state = "unknown"`.
- The alerter's latched incident is separate persisted state and is still open. RECOVERED never posts.

So the dashboard reads `unknown`, Slack holds an unresolved incident, and the operator reconciling the two is looking at a contradiction - permanently.
§7.1's "Limitation" paragraph asserts "On a box with no dispatches it stays `unknown` and says nothing", which contradicts the state machine: once `failing`, no dispatches does not return it to `unknown` in the alerter, only in the detector.

**What should change:** state the relationship explicitly. Either (a) the alerter closes the incident (without a RECOVERED post, or with a "signal lost" post) when the detector returns `unknown` for the whole lookback, or (b) the incident carries a stated maximum open duration. Pick one and name it. Also delete or rewrite the §7.1 Limitation sentence so it does not claim coverage the state machine does not give.

### F3 - MAJOR - "opens exactly three times" does not reproduce; §11 turns a harness artifact into an acceptance test

**Location:** §3.2, lines 214-227 (the table and "Three opens in 14 weeks"); §1.1 W5 line 28; §14.5 X5 line 1100; §11 acceptance check, lines 900-904.

My independent implementation of the §6.2 condition over the whole registry opens **twice**, not three times, and the first open is at 23:04:15, not the table's 22:39.

```
=== A: strict spec recovery rule (close only on a post-open completed): opens = 2
   2026-07-30 23:04:15 "you've hit your session limit · resets #:#am (utc)"
   2026-08-03 21:09:10 'agent process died without reporting a terminal status'

=== B: with lookback reset (spec's stated simulation behaviour): opens = 2
   (identical)

=== READING 2 with latch (looser interleave rule): opens = 2
   (identical)
```

The condition **holds** at 14 distinct moments (11 in July, 3 on 08-03); the dedup latch collapses those to 2 opens.
The spec's row 1 ("07-30 22:39") is the **first** failure's `terminal_at`, which is an N=1 moment, and row 2 ("07-30 23:48") never materialises: the inter-failure gap in that window maxes at 26 minutes, so the 1 h lookback never empties and never "resets".
Those two timestamps are consistent with a simulation that bucketed history into tumbling 1 h windows and reported each bucket's first failure, which is not the stated sliding-window condition.

§3 itself already contains the correction ("the detector sees `terminal_at`, so the N=3 open lands at 23:04:15"), which contradicts §3.2's own table.

**What should change:** correct the §3.2 table to two opens at 23:04:15 and 21:09:10, publish the "condition holds at 14 moments, latch collapses to 2" figure since that is the number that justifies the dedup, and **delete the §11 acceptance check**. ### F5 - MAJOR - §6.3's terminal-writer inventory is incomplete, and the `status="error"` exclusion rests on a false premise

**Location:** §6.3, lines 563-594.

The spec says "Every writer of a terminal status at `83bebe49`, from `grep -rn "TERMINAL_FAILED\|TERMINAL_CRASHED\|mark_terminal" bobi/ --include=*.py`, with every hit classified."
That grep is blind to terminal statuses written through `registry.update(status=...)`. Three such writers exist:

```

...plus the seven bobi/session.py sites the spec does list
$ awk '/^ *(async )?def /{d=NR": "$0} NR==2394{print "2394 in -> "d} NR==2419{print "2419 in -> "d}' bobi/subagent.py
2394 in -> 2351: def _run_verdict_agent_blocking(
2419 in -> 2351: def _run_verdict_agent_blocking(
```

Three consequences:

1. **The `error` exclusion's justification is wrong.** §6.3 says `status="error"` "is written only by `bobi/session.py` ... the persistent-session path ... it is the director's own state, already handled by `DEAD_STATES`". `subagent.py:2394` and `:2419` write `error` from `_run_verdict_agent_blocking`, a **dispatched** sub-agent, on timeout and on attempt exhaustion. `DEAD_STATES` only restarts on the director's own `/health` status (`supervision.py:730-731, 740-745`), so those failures are handled by nothing: not the restart path, not this detector. That is a real dispatch-failure class excluded on a false premise, and it is the same class as §3.2's `turn failed` cluster.
2. **`sdk.py:542` `mark_done` writes `"done"`,** which `sdk.py:46` lists in `TERMINAL_STATUSES` as a legacy success alias. It is live: `orchestrator.py:169` calls it as a defensive fallback. Under the spec's literal rules a `done` success neither breaks the streak ("no `completed` session interleaved") nor closes an incident (recovery = "reached `completed`"). Latent today (0 `done` entries) but a silent hole.
3. **`subagent.py:2675` `cancel_agent`** writes `status="cancelled"` with no `terminal_at`, which is where all 38 `cancelled` entries with `terminal_at == 0.0` come from. Harmless for the detector, but test 10c calls that shape a "legacy entry" when it is a current writer.

Two grep hits are also in neither of §6.3's two lists: `subagent.py:548` and `:553` (they call `_persist_terminal`, so they are covered in substance by the `:326-338` row, but the "every hit classified" claim is not met), as are `sdk.py:544`, `:596`, `:599`.

**What should change:** derive the inventory from the status vocabulary, not from `mark_terminal`. Re-justify the `error` exclusion on the real grounds (it carries no `terminal_at` from several writers and is written by the director on recoverable turn failures), or bring dispatched-session `error` into scope. State explicitly that `done` breaks a streak and closes an incident, or that it is deliberately ignored.

### F6 - MAJOR - the stated normalization rule cannot satisfy test 10b

**Location:** §6.2 lines 518-523 (the rule) and 536-543 (the empty-signature rule); §11 test 10b, line 871.

The rule is: first line, lowercased, digit runs collapsed to `#`, truncated to 120 chars; and "a normalized signature that is empty or whitespace-only is **not a signature**."
Test 10b asserts "an all-digits error does not become a universal match."
The rule does not deliver that:

```
$ PYTHONPATH=.../1008r2-main python3 -c "<the stated rule>"
  raw='500'              -> sig='#'       rejected_by_stated_rule=False
  raw='404'              -> sig='#'       rejected_by_stated_rule=False
  raw='0'                -> sig='#'       rejected_by_stated_rule=False
  raw='429\nsecond line' -> sig='#'       rejected_by_stated_rule=False
  raw=''                 -> sig=''        rejected_by_stated_rule=True
```

`"500"` and `"404"` both normalize to `"#"`, match each other, and pass the empty-signature guard.
Three unrelated numeric errors would open an incident whose alert quotes `#`.

I also checked for live collisions and found none, so this is latent like the empty-signature case:

```
=== normalization collisions (one signature, >1 distinct raw first line): 0
```

**What should change:** add the missing clause to §6.2 - a signature with no alphabetic character is not a signature - so test 10b has something to test.

### F7 - MAJOR - the 500 cap does not bound the thing §6.4 says it bounds

**Location:** §6.4, lines 626-634.

"Cost becomes O(recent) parses over an O(dirs) stat sweep. The stat sweep is the part that grows without bound, so it takes a hard cap: examine at most the 500 most-recent entries by mtime and stop."

You cannot know which entries are the 500 most-recent by mtime without statting all of them.
The cap therefore bounds **parses**, which the lookback already bounds, and leaves the stat sweep exactly as unbounded as before.
And the parse bound is already slack by orders of magnitude:

```
total entries with started_at: 856
span: 2026-07-25 17:33 .. 2026-10-09 05:09  (75.5 days)
mean dispatches/hour: 0.47
PEAK dispatches in any 1h window: 27 (ending 2026-07-31 21:54)
PEAK terminal events in any 1h window: 19 (ending 2026-08-18 22:53)
500 cap / peak hourly terminals = 26.3x
500 cap / mean hourly = 1058x
```

**What should change:** cut the cap (see §5, item 3) or restate it honestly as a parse cap with the real headroom figure. §6.4's "roughly 100x the real hourly rate" matches neither the mean (1058x) nor the peak (26x) - see F16.

## 5. Simplicity verdict

The bar is the simplest practical solution with no cruft.
I agree with all four of §1.3's cuts. Here is what that pass did not cut.

### 1. `sessions_failing` / `sessions_recovered` - **CUT**

Lost capability: none that anyone can name.
Nothing in this repo subscribes to `fleet/lifecycle`'s episode events for any consumer-side behaviour; §14.5 concedes the pair is unconsumed and keeps it only for "consistency with a precedent".
"Consistency with a precedent" is not a capability. Under a no-cruft bar an unconsumed event pair is the definition of cruft, and `load_grace`'s pair is not an argument that a *second* unconsumed pair is free - it is an argument that one already shipped.
The pair is also pure addition later: adding a lifecycle event is a two-line edge in `telemetry.py` plus a doc row, with no migration and no consumer breakage. That makes it the cheapest thing in the spec to defer and the cheapest to regret keeping.
Keeping it also forces a doc change (`ADMIN_PROTOCOL.md` lifecycle table) that would otherwise be a one-line heartbeat-schema addition.
If anything survives on consistency grounds it should be the **heartbeat block**, which has a stated consumer path (the deferred dashboard chip, §10), not the episode pair, which has none.

### 2. `supervisor-session-incident.json` - **KEEP**

Lost capability if cut: nothing, but the cost of cutting is a migration.
`alerting.py:122-128` really does `unlink` the whole file, and I verified `_check_recovery` at `:231` calls `_clear()` before posting RECOVERED, so a shared file genuinely loses an open crash-loop incident's `exhaust_cycles`.
`brain_availability.py:23` is a real in-repo precedent for a second small state file, and #1097 is real evidence that the existing file carries an ordering contract.
This is the one "extra" component in the spec that pays for itself.

### 3. The 500-entry cap - **CUT**

Lost capability: none. It does not bound what it claims to bound (F7), the lookback already bounds parses to a measured peak of 19 per hour, and 500 is 26x that peak.
Deleting it removes a constant, a sort, and a paragraph, and loses no protection.
If growth-proofing is wanted, the honest version is a parse-count guard with a logged warning, or nothing at all until registry pruning lands (already correctly out of scope).

### 4. `WATCHDOG_SESSION_FATAL_ENABLED` - **KEEP**; `WATCHDOG_SESSION_FAIL_STREAK` - **CUT**

The kill switch earns its place on the stated grounds: this is the first sidecar feature that reads a shared on-disk surface the manager writes concurrently, and `WATCHDOG_LOAD_GRACE` (`config.py:81`, `:105`) is an exact precedent for shipping one. Losing it means a rollback is the only remedy.

The streak knob does not. §1.3 cut the lookback knob with the argument "nobody has asked to tune it, and promoting a constant to a knob later is additive and free" - that argument applies verbatim to N.
Q2 calls N "genuinely arguable", but an arguable *default* is a reason to pick a default carefully, not a reason to ship a knob: §6.2's own table shows the entire range of the argument is 4 minutes of latency.
Cut it, pick 3, and promote it if an operator ever asks.
That takes §9 from two knobs to one and deletes a config field, an env parse, and a test.

### 5. The `unknown` third state - **KEEP**

Lost capability if cut: the ability to distinguish "this supervisor evaluated and found nothing failing" from "this supervisor is too old to know".
The spec's own reasoning is right and `load_grace: null` (`ADMIN_PROTOCOL.md:323`) is the exact precedent.
But F2 means `unknown` currently has an unspecified relationship to the alerter's latch, which has to be fixed, not by cutting the state.

### 6. Single-flight memoization - **KEEP, but simplify the mechanism**

Lost capability if cut by making the alerter the only caller: the heartbeat stops carrying `session_health`, which is Shape R's entire point. So "alerter only" is Shape M, not a simplification of R.
The E1 inconsistency it prevents is real and cheap to hit (two scans against a concurrently-written registry).
But "memoized on the poll timestamp" is more machinery than the problem needs: `CompositeObserver.poll` (`supervision.py:205-208`) already fans one `SupervisorState` out to both observers in one pass, so the observation can simply be computed once in the composite's caller and handed down, or attached to `SupervisorState` the way `load_grace` already is (`supervision.py:169`).
That removes a memo cache and its invalidation question, and deletes test 10d's need to count invocations.
**Recommend: compute once per poll and pass it, not a memo keyed on a timestamp.**

### 7. `last_ok_at`, `since`, `failures` in the published block

- `failures` - **KEEP.** The alert message (§7.3) quotes "the last 3 sessions", so the count is already a stated consumer.
- `since` - **KEEP.** The RECOVERED notice reports "the incident duration" (§7.1), which needs an open timestamp, and §7.3's message says "none completed in 28m".
- `last_ok_at` - **CUT.** No stated consumer reads it. The alert does not quote it, the RECOVERED duration is computed from `since`, the recovery rule compares against the incident's `opened_at` and not against `last_ok_at`, and the deferred dashboard chip needs only `state`. It also costs the detector an extra pass over the lookback to find the most recent success. Lost capability: an operator cannot see "last good dispatch" in the heartbeat - and `terminal_at` in the registry already answers that, which is exactly the argument §1.3 used to cut session lifetime.

### 8. The test list

- **Redundant: 2 and 4.** Test 2 ("N failures with different signatures -> `ok`") and test 4 ("`resets 12:40am` and `resets 1:05am` match after digit collapse") are the two halves of one discriminator, and 10b already unit-tests the normalizer including digit collapse. Fold 4 into 10b and keep 2.
- **Redundant: 3 and 13.** Both are about a `completed` not counting. 3 asserts a `completed` inside the streak prevents an open; 13 asserts a pre-incident `completed` does not close one. Different enough to keep both - this is the one pair I would NOT merge, because finding 6 was the near-ship defect.
- **Asserts the same thing twice: 6 and 10a.** Both assert "-> `unknown`, never `failing`" on a degenerate input. Keep both; they are two different degenerate inputs and the empty-signature one is a verified codepath.
- **10d - CUT** if recommendation 6 above is taken (there is no invocation count to assert once the observation is computed in the composite and passed down).
- **10b - KEEP but it currently asserts the unimplementable** (F6). Fix §6.2 first.
- **10 - KEEP and EXTEND** past the grace boundary (F1). As written it tests the bug.
- **12 and 14 - KEEP.** Both are single-purpose and neither duplicates another.
- **17 - KEEP.** This is the only test that proves point 3 of the issue end to end, and it is the strongest item in the plan.
- **The "exactly three opens" acceptance check - CUT.** It is not a legitimate test. It reads `/data/.bobi/agents/eng-team/run/state/sessions/`, an absolute path on one Fly volume that no CI runner has; `grep -rn "run/state/sessions" tests/` returns nothing, so nothing in the suite does this today. The registry is unpruned and moved from 848 to 855 `state.json` files during this review. And its expected value is wrong (F3). It is a fixture that rots on the next dispatch. The right artifact is what the spec already has: §3.2 as a recorded measurement in the design doc, plus synthetic fixtures (tests 1 and 10) built from the real entries, which is what tests 1 and 10 already specify.

### 9. The 10-file scope - **all ten are necessary under R**

I checked each against the recommended shape and found nothing droppable:
`probe.py` (detector), `config.py` (the kill switch, even at one knob), `snapshot.py` (`build_heartbeat` at `:136-178` is the literal payload dict, so R cannot publish without it), `telemetry.py` (the only caller seam), `alerting.py` (the incident edge), `ADMIN_PROTOCOL.md` (the schema is normative and the repo's own rule is docs in the same PR), three test files matching the three code seams, and the stub fixture for test 17.
Cutting the episode pair (item 1) does **not** remove a file: `telemetry.py` and `ADMIN_PROTOCOL.md` are both still needed for the heartbeat key.

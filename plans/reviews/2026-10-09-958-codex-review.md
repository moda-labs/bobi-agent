### F1 - BLOCKER - Posting before subscribing loses fast human replies

- **Claim in the spec:** §3 steps 2-3: post the ask, then “Block until a human replies”; §3.2 factors `_wait_for_code` into the waiter used after posting.
- **What main actually says:** `bobi/events/client.py:207-211` says the subscription must be live first: “Replay is recovery, not a substitute for establishing the requested live subscription first.” `bobi/inbox.py:444-447` explicitly enforces “Subscribe before publish.” A deployment is not placed in the subscription index until `event-server/core/src/core.ts:1465-1471`.
- **Why it matters:** If Slack returns the ask’s `ts`, the human immediately replies, and registration has not completed, no `login-bootstrap` deployment exists to receive that event. Replay is per deployment (`docs/EVENT_SERVER.md:434-441`), so a deployment created afterward cannot replay an event it was never admitted to. The command then waits until timeout despite a valid “ready” reply.
- **Fix:** Open and connect the event-bus listener before posting the ask. After `wait_connected`, post the ask, obtain its `ts`, install the thread predicate, and consume queued events. Verification must assert listener-connected -> ask posted -> reply consumed -> login spawned, not merely reply consumed -> spawn.

### F2 - BLOCKER - Concurrent runs are destructive, not cosmetic

- **Claim in the spec:** §5 Q3: “The residual race is cosmetic” and produces only duplicate Slack messages.
- **What main actually says:** Every waiter registers under the fixed name `"login-bootstrap"` at `bobi/auth_bootstrap.py:543-546`. Registering the same name in the same bubble explicitly supersedes the earlier deployment and removes its subscriptions at `event-server/core/src/core.ts:1441-1451`.
- **Why it matters:** Two concurrent runs can post two asks. The second registration removes the first listener from the subscription index. A reply to the first thread is delivered only to the second listener, whose thread predicate rejects it. The first command starves until timeout. If both reach login, two CLIs can also race while writing the same credential. This is not message tidiness.
- **Fix:** Enforce one active run per machine and target with a non-blocking per-target lock. The second invocation should report the existing pending ask. Use a unique deployment name as defense in depth, but a unique name alone does not prevent concurrent credential writers. Add a real two-process test.

### F3 - BLOCKER - New root `chown` operations permit symlink-based ownership attacks

- **Claim in the spec:** §3.4 prescribes root-run `chown "${APP_USER}:${APP_USER}" "${DATA_DIR}/codex"` and two root-run `chown ... "${CODEX_HOME}/auth.json"` calls. It characterizes the three-line section as having no destructive path and says no entrypoint path produces problematic ownership.
- **What main actually says:** The entrypoint runs as root (`docker/docker-entrypoint.sh:5-8`) and makes the durable volume app-owned (`docker/docker-entrypoint.sh:370-378`). Thus the `bobi` user can replace `/data/codex` or `auth.json` with a symlink between boots. Main already performs this unsafe directory `chown` only inside the codex-brain branch at `docker/docker-entrypoint.sh:486-488`; the spec expands it to every brain.
- **Why it matters:** A compromised worker can leave `/data/codex -> /etc`. On the next Claude-brain boot, `mkdir -p` follows the link and ordinary `chown /data/codex` dereferences it, changing ownership of `/etc`. Similarly, `auth.json -> /etc/shadow` makes the proposed auth-file `chown` transfer ownership of a root file to `bobi`. The subsequent root materializer also follows an `auth.json` symlink when `Path.write_text` runs at `docker/docker-entrypoint.sh:324-330`.
- **Fix:** Before any root operation, use `lstat` semantics and reject symlinks or non-directories at `${DATA_DIR}/codex`. Never `chown` an app-controlled credential pathname by following it. Validate as root or reject/remove only the symlink itself before materialization. Add container tests planting directory and file symlinks to protected targets.

### F5 - MAJOR - The unconstrained target and guard scoping bypass gateway and shadow-auth protections

- **Claim in the spec:** §3.3 sets `os.environ[BRAIN_ENV] = target` and gates both existing refusal guards on `target is None`.
- **What main actually says:** `_active_spec()` silently falls back to Claude for any unknown value at `bobi/auth_bootstrap.py:117-120`. The gateway guard says such teams authenticate through runtime gateway credentials at `bobi/auth_bootstrap.py:614-625`. `_spawn_login` launches the provider CLI directly and removes only `spec.shadow_env` at `bobi/auth_bootstrap.py:209-224`.
- **Why it matters:**
  - `login-bootstrap typo` disables both guards but silently resolves the Claude spec.
  - `login-bootstrap claude` disables the Claude shadow-env guard. It can mint OAuth that `ANTHROPIC_API_KEY` will continue to outrank.
  - `login-bootstrap codex` on a Claude gateway disables the gateway guard and invokes `codex login --device-auth` directly against the provider. The earlier superseded plan correctly identified this as bypassing the gateway’s audit/spend boundary.
- **Fix:** Make the CLI target an explicit choice, initially `codex` only. Reject unknown values rather than relying on `_active_spec` fallback. Preserve a gateway refusal unless product policy explicitly authorizes direct provider credentials on gateway teams. Apply the shadow guard according to the resolved provider, not merely whether an argument was supplied.

### F6 - MAJOR - A revoked or wrong credential makes the advertised 401 recovery a no-op

- **Claim in the spec:** §3.5 says a worker reporting a codex 401 causes the director to run `login-bootstrap codex`. §6 says codex OAuth has “no refresh expiry” and is once per machine.
- **What main actually says:** Codex validation checks only that a nonblank refresh token is present (`bobi/auth_bootstrap.py:162-171`). It does not prove the token is accepted, unrevoked, or belongs to the desired account. Structurally valid credentials short-circuit the operation at `bobi/auth_bootstrap.py:629-633`; the CLI has an earlier short-circuit at `bobi/cli.py:827-829`.
- **Why it matters:** A revoked token, server-invalidated token, or credential for the wrong account can produce a real 401 while still passing the structural check. The director runs the documented recovery, which prints “already present” and does nothing. A machine changing brain or account has the same problem. There is no shell-independent rebind path.
- **Fix:** Add an explicit human-gated rebind/force mode. After the human’s ready reply, quarantine the old credential and start a new login. “No expiry field” should be stated as exactly that, not “never expires.”

### F7 - MAJOR - Q1 does not cover channel or event-server failure at boot

- **Claim in the spec:** §5 Q1 considers only nobody replying and recommends a long bounded wait with reuse of a persisted thread.
- **What main actually says:** Missing `BOBI_LOGIN_CHANNEL` raises immediately at `bobi/auth_bootstrap.py:649-654`. - **Why it matters:**

  - Event server down after a legacy Slack ask posts: the command fails before the timeout, the container restarts immediately, and Option C repeatedly posts into the saved thread.
  - Unset or invalid channel: permanent crash loop with no health endpoint.
  - Option A still leaves no supervisor or status process.
  - Option C’s state is durable read-modify-write state, but the spec specifies neither atomic writing nor locking. Main requires atomic durable state and locking at `bobi/fsutil.py:1-17` and `:161-172`.
  - Two machines post indistinguishable asks because the text names neither machine, agent, nor target.
- **Fix:** Resolve Q1 with a complete failure-state table, including post failure, registration failure, connection failure, timeout, and restart. Persist state atomically under a lock. Include agent, instance, target, and attempt state in the message. Prefer starting an observable supervisor/status process before a long boot wait.

### F9 - MAJOR - Timeout handling loses late replies and can leak a hung login process

## Simpler shape

A smaller design can satisfy Z1-Z5:

1. Scope v1 explicitly to Slack, the channel Z1 requires.
2. Acquire a non-blocking per-target lock before posting.
3. Register a uniquely named listener and wait for its connected frame before posting.
4. Post the ask, capture its `ts`, and filter human replies to that thread.
5. Resolve `codex` through an explicit target choice rather than mutating `BRAIN_ENV` with arbitrary input.
6. Use bounded timeout at both triggers and accept that a boot restart may post a new ask. This is Q1 Option B.
7. Keep the directory-level `CODEX_HOME` design, but harden its path against symlinks.
8. Do not widen the subscription sweep beyond recognized API-key files. Handle malformed or revoked credentials only in an explicit human-approved rebind.

This gives up Option C’s single persistent Slack thread and non-Slack channel support. It removes durable ask state, its locking/invalidation rules, and the destructive unknown-schema sweep.

## 3. New findings

### G1 - BLOCKER - a second restart inside the lookback re-admits the first restart's reaped entries

**Location:** §6.2, lines 590-596 (the exclusion rule) and 598-602 (its input); §11 test 10, line 1088.

**Claim under attack:** "discard any terminal entry whose `terminal_at` falls in `[last_restart_at, last_restart_at + 300s]` for as long as that entry is inside the lookback", sourced from `state.last_restart_at`.

`last_restart_at` is a single scalar, not a history.

```
$ grep -rn "last_restart_at" bobi/supervisor/supervision.py
157:    last_restart_at: float | None
279:        self._last_restart_at: float | None = None
424:        self._last_restart_at = now
789:            last_restart_at=self._last_restart_at,
```

`_note_restart` (def at `supervision.py:416`, the assignment at `:424`) overwrites it on every restart edge, charged or not.
So once restart #2 lands, restart #1's reaped entries are no longer inside `[last_restart_at, last_restart_at + 300s]` and they count again, while still sitting in the 3600 s lookback.

That is the crash loop, not an exotic case.
`SupervisorConfig` ships `max_restarts=3` inside `restart_window=1800.0` with `backoff=(30.0, 60.0, 120.0)` (`config.py:64-66`), so two or three restarts inside one 3600 s lookback is the designed shape of a loop.

Simulated against §3.1's own five-session cluster, the condition applied exactly as §6.2 now words it:

```
08-03 cluster (5):
    2026-08-03 21:09:09.201 crashed wf-issue-lifecycle-eng-team-858
    2026-08-03 21:09:09.989 crashed wf-issue-lifecycle-eng-team-851
    2026-08-03 21:09:10.256 crashed wf-pr-closed-eng-team-adhoc-fa0b931d
    2026-08-03 21:09:16.831 crashed wf-issue-lifecycle-eng-team-884
    2026-08-03 21:09:19.289 crashed wf-issue-lifecycle-eng-team-850

--- (a) last_restart_at = first reap write, constant
   NO OPEN across 2026-08-03 21:09:09 .. 2026-08-03 22:29:09
--- (a2) last_restart_at = 69s before the first reap
   NO OPEN across 2026-08-03 21:09:09 .. 2026-08-03 22:29:09
--- (d) second restart at +120s (crash loop): last_restart_at MOVES
   OPEN at 2026-08-03 21:11:09 sig='agent process died without reporting a terminal status'
--- (d2) second restart at +30s (min backoff)
   OPEN at 2026-08-03 21:09:39
--- (c) last_restart_at = reap - 400s (reap write lands outside the 300s window)
   OPEN at 2026-08-03 21:09:39
```

Rows (a) and (a2) are what the fold fixed: with one restart the exclusion holds at every poll time, which is a real improvement over the drafted grace.
Rows (d) and (d2) are the hole.
Row (c) is a third, smaller hole: `terminal_at` is stamped at *reap* time, not death time (`sdk.py:592-593` and `reconcile.py:132-133`), so a manager that takes longer than 300 s to come back up and serve the `/health` read that triggers `_reap_if_dead` writes its orphans outside the window.

Test 10's three stated clock positions (inside the window, grace + 1 s, grace + 30 min) all pass under the fixed rule, so the test as specified does not reach this.

**What should change:** exclude entries against a *set* of recent restart instants, not the last one, and state the retention explicitly.
`RestartBudget._stamps` (`supervision.py:114`) already keeps the windowed restart timestamps, but its window is 1800 s against a 3600 s lookback, so the stamp list must be retained for at least the lookback rather than reused as-is.
Test 10 needs a fourth clock position: a second restart after the first, asserting still no edge.

### G2 - BLOCKER - `last_restart_at` is `None` on a fresh supervisor, which is exactly when the mass reap happens

**Location:** §6.2, lines 598-602; §14.6 "What this round could not verify", item 2.

`_last_restart_at` is initialised to `None` (`supervision.py:279`) and is never persisted.
The only supervisor state that survives a process exit is the incident file and the admin cursor:

```
$ grep -rn "atomic_write_json\|state_path" bobi/supervisor/*.py
bobi/supervisor/admin.py:218:        cursor = ... / "admin-cursor.json"
bobi/supervisor/alerting.py:96:            state_path = paths.state_path(project_root) / STATE_FILE
bobi/supervisor/supervision.py:304:        return paths.state_path(self.project_root) / "manager-health.port"
```

So on every path where the supervisor itself is replaced, the exclusion cannot fire:

```
--- (e) last_restart_at = None (fresh supervisor boot / host reboot)
   OPEN at 2026-08-03 21:09:39 sig='agent process died without reporting a terminal status'
```

Those paths are not rare.
`EXIT_BUDGET_EXHAUSTED = 70` (`supervision.py:74`) is returned at `:628` and `:664`, so budget exhaustion deliberately exits and lets the machine restart - which is the end state of the crash loop whose reaps this guard exists to suppress.
A host reboot or an OOM kill of the supervisor lands in the same place.

This also reverses the status of round 1's unverified item.
§14.6 carries forward "Whether §3.1's reap was a *manager restart* specifically rather than a host reboot or an OOM kill ... F1's conclusion does not depend on which it was."
That was true of round 1's finding and is false of the fix: whether the fix covers the spec's only measured false positive depends entirely on whether the supervisor survived.
The best available evidence points the wrong way.
The local event-server's per-subscriber stream for the old client ends at `2026-08-03T21:07:16` and a new client UUID's stream begins at `2026-08-03T21:09:16`, a two-minute gap, with the five reaps at 21:09:09-19 landing just before the new stream's first event:

```
$ tail events-d1133750-...jsonl | ...   -> last entry 2026-08-03T21:02:18 .. 21:07:16
$ head events-049f338f-...jsonl | ...   -> first entry 2026-08-03T21:09:16
```

That shows the process holding the bus client was replaced after a two-minute outage; it does not prove the supervisor survived, and a two-minute gap is longer than a child respawn.

**What should change:** state the `None` case explicitly and pick a behaviour.
The honest options are to persist the restart stamps beside the incident file, or to treat `last_restart_at is None` with a supervisor uptime under the lookback as "every entry older than this boot is excluded".
Either way §14.6's "does not depend on which it was" disclaimer has to go, because it now does.

### G3 - MAJOR - the detector's `ok` state is undefined, and the real July trace goes `failing -> ok`, not `failing -> unknown`

**Location:** §6 state machine, lines 516-544; §5.2's three-value `state`, line 415; §7.1 ABANDON, lines 892-898.

The spec defines `unknown` ("no recent terminals, or registry unreadable") and `failing` (§6.2).
It never defines `ok`.
The only edge into `ok` in the diagram is from `failing` "by a session SUCCEEDED and STARTED AFTER the incident" - a predicate that needs the alerter's incident open time, which a pure function of the registry (§6, line 484) does not have.
So the implementor must invent `ok`, and the natural invention is "recent terminals exist and the streak does not hold".

Under that reading the heartbeat publishes an affirmative `ok` with zero successes observed.
Run over the whole history at a 30 s poll grid:

```
poll grid 30s over 75.5 days: 217307 polls
   state=ok        38884 polls   17.9%
   state=unknown  178201 polls   82.0%
   state=failing     222 polls    0.1%
   of which 'ok' with ZERO success in the window: 3475 polls (1.60% of all)
```

And it happens inside the spec's own flagship incident:

```
=== July incident, 30s poll grid, state transitions only ===
   07-30 22:30:00  -> ok        (window: 0 failed, 4 success)
   07-30 23:04:30  -> failing   (window: 3 failed, 2 success)
   07-31 00:49:00  -> ok        (window: 2 failed, 0 success)
   07-31 01:17:30  -> unknown   (window: 0 failed, 0 success)
```

At 00:49:00 the oldest of the three streak failures ages out, the state flips to `ok` with two failures and no successes in the window, and the alerter's incident is still open and unrecovered.
The dashboard reads `session_health: ok` for 28.5 minutes while Slack holds a session-fatal incident.
ABANDON does not help: it fires on `unknown`, and `ok` is not `unknown`, so the timer has not even started.

This is the exact contradiction §7.1 says the ABANDON transition removes and that §6.4's single read exists to prevent.
A shared observation makes both consumers see the same *registry*; it does not make a memoryless three-value state agree with a latch.
Because this deployment's mean dispatch rate is 0.47/hour, a single failing dispatch per hour holds the state at `ok` indefinitely and resets nothing.

**What should change:** define `ok` as a predicate on the window, and state what the heartbeat publishes while an incident is open but the streak no longer holds.
The cheapest truthful fix is a fourth value or a demotion rule: `ok` only when the window contains a success, otherwise `unknown`.
That also makes ABANDON reachable from every post-`failing` state instead of one of them.

### G4 - MAJOR - the ABANDON timer is not specified well enough to implement, and it is the dominant close path, not a corner case

**Location:** §7.1, lines 892-898; §11 test 16, line 1120; §11 test 14, line 1118.

"One full lookback window of `unknown` with an incident open clears it" leaves three things unstated:

1. **When the window starts.** The first `unknown` poll, the last `failing` poll, or the incident's open time. These differ by up to an hour.
2. **Whether the timer is persisted.** Test 14 requires the incident to survive a process restart via the state file. If the abandon clock is in-memory, a supervisor restart resets it and the incident never abandons on a box that restarts more than once an hour. If it is persisted, it belongs in `supervisor-session-incident.json`, which §7.2 does not mention.
3. **What resets it.** G3 shows the real trace passes through `ok`, so "a whole window of `unknown`" is not reached by simply stopping dispatch.

§7.1 frames abandon as the low-traffic case ("a low-traffic deployment reaches it on its own").
Measured, it is the normal case: 82.0% of all polls over 75.5 days see an entirely empty one-hour window (G3's table).

The consequence for the July incident is that RECOVERED never posts:

```
incident open (alerter opened_at): 07-30 23:04:15
last session-limit failure terminal_at: 07-31 00:17:05
heartbeat reaches 'unknown' at: 07-31 01:17:30
abandon earliest possible (unknown + 3600s): 07-31 02:17:30
first success that STARTED after the open:
   started 07-31 05:42:47  terminal 07-31 05:45:08  wf-pr-closed-eng-team-adhoc-b1873a84
=> RECOVERED would post at 07-31 05:45:08, 400.9 min after the open
```

Abandon at 02:17:30 precedes the first provable recovery at 05:45:08 by 3 h 28 min, so the operator gets one alert at 23:04 and then silence, for an outage that self-healed at 00:40.
The spec's reasoning for posting nothing on abandon is defensible, but Gate 1 should be told that on this deployment's traffic this is the expected outcome and the RECOVERED notice (and test 12, and `since`) is close to dead code.

**What should change:** name the timer's start instant, say where it lives, and state that abandon is the expected close path at this dispatch rate rather than an edge case.

### G6 - MAJOR - `since` cannot be both the heartbeat's per-poll field and the alerter's incident open time

**Location:** §5.2, lines 413-428; §7.1 CLOSE, line 865.

§5.2 publishes `"since": "2026-07-30T23:04:15Z"` in the detector's block and says "`since` is what the RECOVERED notice computes its duration from (§7.1)".
The detector is memoryless, so its `since` must be re-derived from the current window every poll, while the RECOVERED duration must be measured from the alerter's persisted open time in `supervisor-session-incident.json`.
Those two drift apart as the streak advances:

```
the 13 session-limit failures, terminal_at:
    07-30 22:39:35 ... 07-30 23:04:15 ... 07-30 23:48:30 ... 07-31 00:17:05
At the final hold (07-31 00:17:05) the last 3 failures are 07-30 23:48:30 .. 07-31 00:17:05
memoryless 'since' (oldest of last 3) = 07-30 23:48:30 ; alerter opened_at = 07-30 23:04:15
understatement = 44.2 min
```

A RECOVERED notice computing its duration from the published `since` would report 44 minutes less than the real incident on the spec's own incident.
Sourcing it the other way, telemetry reading the alerter's state file, breaks both §6.4's single-observation model and §7.2's separation of the two files.

ABANDON makes a second state reachable that the spec does not address: after abandon the incident file is unlinked (`alerting.py:122-128`), so `since` is gone, while the detector may still be publishing a `since` from the same entries if they are inside the lookback but discarded by the restart exclusion.
Under G1 a subsequent restart then re-admits those entries and re-opens the incident from the same data, which is a repeating alert for one event.

**What should change:** say explicitly that the RECOVERED duration comes from the alerter's own `opened_at`, and define what the block's `since` means as a per-poll derivation (and whether it is the streak's first or Nth failure).

### G7 - MINOR - test 8's mtime assertion is vacuous against the fixture the spec gives it

**Location:** §11 test 8, line 1086.

"The detector performs no writes. Assert `state.json` mtimes are unchanged across a detection run."

The mtime half is sound: `_write_state` calls `atomic_write_json` -> `atomic_write_text`, which writes a temp sibling and `os.replace`s it (`fsutil.py`), so any write produces a new inode and a new mtime, and in a unit test with a tmp fixture no other process touches the tree.

The problem is that the write the test is guarding against cannot happen with terminal fixtures.
`_reap_if_dead` returns immediately for a non-active status and for a zero pid:

```
$ sed -n '588,593p' bobi/sdk.py
        if entry.status not in ACTIVE_STATUSES:
            return entry
        if not entry.pid or pid_alive(entry.pid):
            return entry
        msg = DIED_WITHOUT_TERMINAL
        self.mark_terminal(entry.name, TERMINAL_CRASHED, error=msg)
```

So a detector that wrongly calls `list_active()` over a fixture of `failed`/`crashed` entries with `pid: 0` writes nothing, and test 8 passes.
§4.1 F1, the defect it exists for, only fires when an ACTIVE entry with a dead pid is present.

**What should change:** either require the fixture to include an active entry with a dead pid, or assert the API directly by monkeypatching `SessionRegistry.list_active` and `mark_terminal` to raise.
The second is the stronger assertion and does not depend on filesystem timestamps at all.

### G9 - MINOR - test 16 asserts a property the revised design does not have

"the heartbeat reads `unknown` rather than contradicting an open incident".

Before abandon fires, the heartbeat reads `unknown` *while* the incident is open, for a full lookback window by design.
That is the contradiction, not the absence of one.
After abandon the incident is cleared, so there is no open incident to contradict.
There is no state in which "reads `unknown` rather than contradicting an open incident" is the thing being asserted.

**What should change:** split it. Assert the incident file is cleared, assert no RECOVERED post, and assert the bounded contradiction explicitly ("the heartbeat reads `unknown` while the incident is still open, for at most one lookback window").
The last assertion is the honest statement of what ABANDON buys.

## 4. Simplicity verdict on the revision

**Should still go.**
`bobi/supervisor/telemetry.py` (G5).
Once the episode pair is cut, an additive heartbeat block reaches the wire through `snapshot.py` alone, because `build_heartbeat` already takes the whole `SupervisorState`.
Dropping it takes the file count back down and removes the one seam in the design that has no remaining job.

**Should have been kept, or rather fixed instead of trimmed.**
Nothing the fold cut should come back.
All six cuts hold up under re-derivation, including the two I checked hardest: the 500 cap could not bound the sweep (26.3x the measured peak of 19 terminals/hour), and `last_ok_at` really is unused, because the alert's "none completed in 29m" is the streak age, derivable from the same window (verified against the July data).

**Keep, now with a measured basis.**
The bounded reader, at 8.5 ms versus 25 ms for an unbounded parse, is about three lines against an idiom the repo already uses twice.
That is cheap enough to keep even though the absolute saving is 0.03% of a 30 s duty cycle; the growth curve (+169% listdir entries since the draft, parse 12.1 -> 25 ms) makes it the right default.
`supervisor-session-incident.json` and the kill switch both survive re-examination unchanged.

**The one place the revision is now under-simplified rather than over-built** is the three-value `state` vocabulary (G3).
A value with no definition, whose only diagram edge needs state the producer does not have, is not simpler than a defined four-value enum or a demotion rule; it is just unspecified.

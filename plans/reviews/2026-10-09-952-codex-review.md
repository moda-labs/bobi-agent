Codex adversarial review: OpenAI Codex v0.144.5 (codex-cli 0.144.5), model `gpt-5.6-sol`, reasoning effort high, sandbox read-only, session `01a1217c-9b55-7b73-9085-14a6b4052ff6`, 184,480 tokens; spec reviewed at `7a4bac2ccad37221fc1deeb9903c9ff2f344a5dc` against `origin/main` `70db2e1059fdf8f35751b17806496cb91f427b09`; output below is verbatim and unedited.

VERDICT: REQUEST CHANGES

Revision 5 fixes most earlier findings, but it remains unsafe to implement. The CLI can mutate protected per-session topics, the deaf-reconnect callback bypasses the proposed lock, and a crash between the remote PUT and local record write can silently undo a successful change. It also relies on a stale deployment file as proof that the manager is running—an assumption contradicted by current main’s new service-supervision code.

## Findings

### F1. Raw topic edits can delete the manager inbox or recreate the cross-session leak
- **Severity**: blocker
- **Axis**: C
- **Spec claim**: “Monitor topics, lifecycle topics and `inbox/<session>` are NOT in this file.” (`spec.md:188-189`) and “Nothing is recomposed, so monitor, lifecycle and `inbox/` topics pass through untouched by construction.” (`spec.md:318-319`)
- **Evidence**: The manager’s inbox is protected composition state:

  `main-source/bobi/session.py:1657-1660`
  ```python
  keys = [f"inbox/{self.name}"]
  for key in self._subscribe:
      if key not in keys:
          keys.append(key)
  ```

  But non-global inbox topics require no resource authorization:

  `main-source/event-server/core/src/core.ts:406-414`
  ```ts
  // Everything else (inbox/*, reply/*, monitor/*, agent/*, custom topics)
  // is bubble-scoped.
  const GLOBAL_TOPIC_PREFIXES = ["github:", "linear:", "slack:", "whatsapp:", "discord:"];
  ```

  The existing server test proves an arbitrary inbox topic is accepted:

  `main-source/event-server/test/core.spec.ts:2251-2262`
  ```ts
  await handleUpdateSubscriptions(store, "d1", "key1", { add: ["inbox/d1"] });
  expect(store.subscriptions.get("bub_abc:inbox/d1")?.has("d1")).toBe(true);
  ```
- **Why it matters**: `subscriptions remove inbox/<manager>` leaves the workspace file unchanged because that key is absent there, but step 5 independently removes it from the accepted set. The authoritative PUT then makes the manager unaddressable. Conversely, `subscriptions add inbox/<worker>` subscribes the manager to another session’s messages, recreating the isolation incident described in `test_event_isolation.py`. Neither operation requires a grant, and `list` will not flag the missing derived topic.
- **What to change**: Compute the server mutation from the actual workspace delta, not directly from command arguments. A remove may alter the accepted set only if the topic was actually removed from the prior workspace list. Reject `inbox/` topics in the workspace reader and CLI. Add tests for removing the manager inbox and adding another session’s inbox.

### F2. The deaf-reconnect PUT is a fourth mutator that bypasses the accepted-set lock
- **Severity**: blocker
- **Axis**: C
- **Spec claim**: “all three writers take `file_lock` on this file” (`spec.md:280`) while `_resubscribe_on_deaf` “reads its OWN session’s record and PUTs that” (`spec.md:275`).
- **Evidence**: Deaf repair runs asynchronously:

  `main-source/bobi/events/client.py:440-446`
  ```python
  if self._needs_resubscribe:
      ...
      threading.Thread(
          target=self._safe_resubscribe, args=(cb,),
          daemon=True, name="event-client-resub").start()
  ```

  The current hook performs an unlocked authoritative PUT:

  `main-source/bobi/subagent.py:1974-1982`
  ```python
  def _resubscribe_on_deaf() -> None:
      ...
      _put_subscriptions(es_deployment, es_key, active_subscriptions)
  ```

  Locks protect only cooperating callers:

  `main-source/bobi/fsutil.py:163-172`
  ```python
  """Hold an exclusive advisory lock ...
  Advisory, so it only serializes writers that also take it.
  ```
- **Why it matters**: Record `R0` exists. The CLI locks it and PUTs `R1`, but before saving `R1`, the reconnect thread reads `R0` and PUTs it. The CLI then saves `R1`. Final state: record `R1`, server `R0`; `list` may look correct while routing is wrong. The manager-restart race fixed in round 4 has merely moved to the daemon thread.
- **What to change**: The reconnect hook must take the same accepted-record lock across read and PUT. Add a deterministic barrier test that starts the hook between the CLI’s PUT and record save and proves the final server set equals the record.

### F3. The remote PUT and local accepted-set write are not crash-atomic
- **Severity**: blocker
- **Axis**: C
- **Spec claim**: Step 8 says to PUT and “then record the returned set” (`spec.md:327`); the safety argument only says the local JSON write is atomic (`spec.md:278`).
- **Evidence**: The server commits before returning:

  `main-source/event-server/core/src/core.ts:1531-1540`
  ```ts
  await storage.addSubscription(...);
  deployment.subscriptions = desired;
  await storage.putDeployment(deployment);
  return {
      status: 200,
      body: { subscriptions: deployment.subscriptions, ... },
  };
  ```

  The later local write is a separate filesystem operation:

  `main-source/bobi/fsutil.py:143-158`
  ```python
  def atomic_write_json(...):
      return atomic_write_text(
          path, json.dumps(obj, ...), **kwargs
      )
  ```
- **Why it matters**: The server accepts `R1`; then the CLI is killed, the filesystem becomes read-only, or disk-full prevents `save_accepted_subscriptions`. The record remains `R0`. The next deaf reconnect reads `R0` and authoritatively reverts the successful live change. If the local write raises, the command can also report failure even though the server already changed.
- **What to change**: This needs a recovery protocol, not another lock. Prefer a server-backed authenticated read/repair mechanism and remove the local cache as a correctness source. Otherwise write a pending journal before the PUT and require boot/reconnect to resolve pending state before reasserting anything. Test SIGKILL/fault injection after the server commit and a disk-full accepted-record write.

### F4. A deployment record does not prove the manager is running
- **Severity**: major
- **Axis**: A
- **Spec claim**: “Resolve the manager’s session and its live identity” from the deployment and accepted-set files (`spec.md:307-308`), and “no deployment record (the manager is not running)” (`spec.md:332`).

  ```python
  manager = _stop_service_manager(agent_name)
  if manager:
      ...
      _service_action(manager, "stop")
      ...

  ...
  _echo_stop_result(stop_team(project_path, force=force))
  ```

  `EventServerClient.stop()` only closes the socket:

  `main-source/bobi/events/client.py:359-362`
  ```python
  def stop(self) -> None:
      self._stop.set()
      if self._ws:
          self._ws.close()
  ```

  Current main already exposes the real liveness check:

  `main-source/bobi/service.py:842-853`
  ```python
  pid = _read_pid(pid_path) if pid_path.exists() else 0
  manager_running = bool(pid and _pid_alive(pid))

  ```
- **Why it matters**: Stop a supervised manager, then run `subscriptions add`. Both state files remain, so the command proceeds as a live apply. It may start a local event server, mutate an idle deployment, and report success even though no manager is consuming it; if the server discarded the deployment, it exits non-zero instead of taking the specified persist-only path.
- **What to change**: Use `service.team_status(project_path).manager_running`, not state-file existence, to select live versus persist-only behavior. Cover stopped direct, systemd, launchd, and service-restart-delay states with stale deployment files.

### F6. “Malformed” excludes empty and schema-invalid workspace files
- **Severity**: major
- **Axis**: E
- **Spec claim**: The file is “a mapping with one key” (`spec.md:164`), reuses the existing parser (`spec.md:184-186`), and malformed input raises `WorkspaceSubscriptionsError` (`spec.md:206-209`).
- **Evidence**: The parser being reused accepts a scalar string and normalizes every other wrong type to an empty list:

  `main-source/bobi/events/subscriptions.py:13-22`
  ```python

      candidates = [value]
  elif isinstance(value, list):
      candidates = value

      return []
  ```

- **Why it matters**: A truncated empty file, `{}`, `subscribe: {}`, or a list at the document root can become an authoritative empty subscription layer instead of failing loud. ### F7. A valid authorization can be reported as rejected because PUT lacks the existing propagation retry
- **Severity**: major
- **Axis**: E
- **Spec claim**: `add` authorizes new topics and immediately calls `put_subscriptions` (`spec.md:320-327`); the helper contract contains no retry (`spec.md:369-373`).
- **Evidence**: Registration already documents and handles the same consistency window:

  `main-source/bobi/events/server.py:856-868`
  ```python
  On a ``400 unauthorized_topics`` ... almost always means Cloudflare KV has not
  yet propagated a just-written grant — retry ONCE after a short delay ...
  ...
  if _retry_unauthorized:
      time.sleep(0.5)
      return register(..., _retry_unauthorized=False)
  ```

  PUT immediately checks that grant:

  `main-source/event-server/core/src/core.ts:1506-1512`
  ```ts
  const unauthorized = await unauthorizedGlobalTopics(...);
  if (unauthorized.length) {
      return { status: 400, body: { error: "unauthorized_topics", ... } };
  }
  ```
- **Why it matters**: A correct GitHub or Linear credential writes its grant, but the immediate PUT reads stale KV and returns 400. The CLI persists the workspace change and exits non-zero with a false authorization diagnosis. The in-memory local-server tests cannot reproduce this production behavior.
- **What to change**: Give `put_subscriptions` the same bounded one-time retry after authorization. Add a unit test where the first PUT returns `unauthorized_topics` and the second succeeds.

### F8. The server’s replace operation is not failure-atomic after validation
- **Severity**: major
- **Axis**: C
- **Spec claim**: The design and test plan establish “no-partial-write behavior” only for the pre-write authorization rejection (`spec.md:138`, `spec.md:442-443`), but specify no behavior for storage failure during apply.
- **Evidence**: Storage exposes independent operations with no transaction:

  `main-source/event-server/core/src/core.ts:285-292`
  ```ts
  putDeployment(...): Promise<void>;
  addSubscription(...): Promise<void>;
  removeSubscription(...): Promise<void>;
  ```

  Replace executes them sequentially without rollback:

  `main-source/event-server/core/src/core.ts:1522-1536`
  ```ts
  await storage.removeSubscription(...);
  ...
  await storage.addSubscription(...);
  ...
  await storage.putDeployment(deployment);
  ```
- **Why it matters**: A storage exception after two removals but before additions or `putDeployment` leaves the routing index partially changed while the deployment record and local accepted file retain the old set. The client sees an error, but some live routing already changed; `list` cannot reveal it.
- **What to change**: Either provide transactional/compare-and-swap storage semantics or add compensating rollback and an authenticated reconciliation operation. Fault-inject every storage await and assert the final index and deployment record agree.

### F9. The concurrent-add test can pass while one topic is not live
- **Severity**: major
- **Axis**: F
- **Spec claim**: “Two concurrent `add` calls both survive” (`spec.md:474`).
- **Evidence**: The specified algorithm deliberately aborts when the accepted record changed since step 2 (`spec.md:317-318`), while the workspace edits have already composed under their separate lock (`spec.md:314-316`). The real lock blocks rather than rebasing:

  `main-source/bobi/fsutil.py:176-184`
  ```python
  fcntl.flock(lock_file.fileno(), fcntl.LOCK_EX)
  try:
      yield
  finally:
      fcntl.flock(lock_file.fileno(), fcntl.LOCK_UN)
  ```
- **Why it matters**: Both commands read accepted set `R0`. Both workspace topics survive. The first command applies and records `R1`; the second acquires the accepted lock, notices the change, and aborts. A test that merely checks the workspace file passes while the second topic is absent from the server until a manual rerun or restart.
- **What to change**: Specify exit codes and all three final states: workspace, accepted record, and server. The test should require the losing command to exit non-zero, rerun it, and then prove both topics route. Better, rebase under the accepted lock so both commands can complete successfully.

## What the prior rounds missed

- **Round 1** correctly caught loss of `inbox/<self>` through recomposition, but did not test a user explicitly adding or removing reserved inbox topics through the new generic CLI.
- **Round 2** moved accepted subscriptions out of the credential record, but treated only file writers as concurrency participants. It missed the asynchronous reconnect PUT and the remote-PUT/local-write crash boundary.
- **Round 3** found the manager-restart race and demanded an apply-spanning lock, but still modeled only manager and CLI applies. It also accepted a cached “last accepted” set as D4 read-back without proving current routing.
- **Round 4** corrected lock scope for the two manager sites, but the fold still excluded `_resubscribe_on_deaf`. It also could not account for the later PR #1098 service-manager behavior, where stopped managers retain deployment state.
- **All four rounds** missed strict workspace schema validation, KV grant propagation on PUT, and storage failure partway through the server’s replace loop.

## Folds that did not actually fix the finding

- **Round 3 H4 / Round 4 J1**: extending the accepted-set lock across manager apply and write fixed manager-vs-CLI ordering, but not CLI-vs-deaf-reconnect ordering. The callback remains an unlocked authoritative PUT.
- **Round 1 C1 / Round 2’s accepted-cache defense**: recording every successful register/PUT made the cache useful for reconnect, but did not make it “what the server actually routes.” The code explicitly admits the server index can become stale independently.
- **Round 2 G2’s concurrency fold**: moving state into a separate locked file prevented credential clobbering, but did not make the remote server mutation and local state write atomic.

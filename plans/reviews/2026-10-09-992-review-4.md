## Verdict

The fold is mostly sound and the cut design is the right design, but it did introduce new defects, making it three rounds in a row.
Two are genuinely new: §6.1's abandon walk was never re-derived against the reframed clock and is wrong by 31 minutes, and the D5 scope cut invalidated the M-vs-R file arithmetic that §4.3 and Q1 both still quote on the one blocking question.
One BLOCKER survives from round 2 that no round has named: the abandon clock is signature-agnostic while the incident file holds exactly one signature, so a second, different-signature outage is never alerted and the first incident is held open indefinitely.
Separately, three of D1's and D4's load-bearing absolutes are false as written - a third reap path writes a different byte-identical string, a brain-fatal cause can reach `DIED_WITHOUT_TERMINAL`, and `turn failed (kind=unknown, api_status=None)` is a second degenerate signature with 154 live instances.
The reverse check is clean: the cut condition opens on the real July outage, never opens on the 08-03 reap at any poll time, and I found no third case the old design caught and this one misses.
Not ready for a Gate-1 ruling as written: J1 changes behaviour, J6 changes the number Gate 1 is being asked to weigh.

## Fold audit

### D1 - restart apparatus replaced by one comparison

CLAIM.
§2.2 (lines 123-134) and §5.2 (lines 433-440): `DIED_WITHOUT_TERMINAL` (`bobi/sdk.py:50`) is written by exactly two reap sites, no path writes an `error` onto a session before it is terminal, therefore every reap orphan carries that one string and nothing else does, and the one accepted give-up is OOM/SIGKILL.

WHAT I RAN.
I re-ran the AST sweep myself over `bobi/` in `1008r3-main`, collecting every `Call` with an `error` keyword, every call with a `status` keyword, every `SessionEntry(` construction, every `register(` call, and every `atomic_write_json` / `_write_state` / `write_text`.
Then I read `reconcile.py` end to end, traced `/health`'s `manager.status` to its source, and re-grouped the whole registry by signature.

Link 2 (the AST sweep) HOLDS, and it holds for the right reason.
The only call that passes `error=` to `registry.update` is `bobi/session.py:990-995`, and it co-writes `status="error"` in the same call.
`"error"` is not in `ACTIVE_STATUSES` (`bobi/sdk.py:42`), so `is_dead_run` (`bobi/reconcile.py:109-111`) can never select that entry and `reconcile.py:132`'s fallback can never reach it.
All four `SessionEntry(...)` constructions (`session.py:1759`, `subagent.py:1506`, `subagent.py:2284`, `orchestrator.py:321`) pass no `error`, `register()` replaces the file wholesale from `asdict(entry)` (`sdk.py:371-375`), `update()` only writes keys it is handed (`sdk.py:377-399`), and no `atomic_write_json` outside `SessionRegistry._write_state` touches a session state file.
Every other `error=` site is a `mark_terminal` call, which writes a terminal status in the same update.

Link 1 is false as an absolute, and link 3 is false.
There is a third close path on an active entry: `bobi/reconcile.py:200-208`, which writes `error=f"agent exceeded its {entry.timeout}s timeout without reporting a terminal status"`.
It is selected for any active entry past `started_at + timeout + RECONCILE_GRACE` whose pid is alive **or zero** - the pid-0 case `is_dead_run` structurally cannot see, which `subagent.py:1610-1615` documents as the restart-orphan close path in so many words ("would be refused until the reconciler's deadline branch fires at the next manager start").
The registry holds a measured 2-member instance of it (2026-08-20 17:11:36 and 17:11:39, both `reconciled_at` set, both `timeout=3600`, byte-identical signature), and the same orphan event produced a `DIED_WITHOUT_TERMINAL` pair 7 minutes later, so one event split across two strings and the exclusion covers one of them.
On link 3: `bobi/manager_health.py:139` publishes the director session's registry status verbatim as `/health`'s `manager.status`; `session.py:990-995` sets the director to `status="error"` on exactly `ERROR_KIND_AUTHENTICATION` / `ERROR_KIND_CREDITS_EXHAUSTED`; `supervision.py:68` plus `:740-745` restart the manager on that status with no debounce; the restart orphans every in-flight dispatch into `DIED_WITHOUT_TERMINAL`.
So a brain-fatal cause can put the excluded string on 3+ sessions inside an hour, and §5.2:133's "never the brain-fatal shape" does not hold.

The no-restart-coupling claim HOLDS.
`grep -n "restart\|_stamps\|uptime"` over the whole spec returns only arguments against a restart guard (§5.2:452-464), the budget-neutrality proof (§7:727-734), and the alert text.
No design element reads restart state in either direction.

VERDICT: HOLDS on the mechanism, FIX INTRODUCED A NEW DEFECT in the argument.
The exclusion itself is correct and the simulation reproduces, but §2.2's safety argument overstates in two places that a Gate-1 reader and an implementor will both rely on.

What to change: J2 and J5.

### D3 - the abandon clock reframed

CLAIM.
§6.1 (lines 609-616): abandon is "the condition has not held for a full lookback window (3600s)"; the clock is `last_failing_at`, re-stamped on every poll where the condition holds, initialized to `opened_at` at open time so it is never absent.
§6.1:643-649 walks it against the July incident and claims abandon fires at 01:17:05.

WHAT I RAN.
I re-implemented §5.2 from its text alone, enumerated all 13 session-limit failures by `terminal_at`, and walked a 30s poll grid forward from the open.

Open, no further holds: abandon at `opened_at + 3600`.
Reachable and bounded, because the init rule removes the null. Correct.

Open, supervisor process replaced mid-incident: no interaction at all now, because nothing discards entries on a boot boundary.
Round 3's H6 is genuinely dead, and this is the fold's best result.

The claimed 01:17:05 is wrong.
The last session-limit failure is at 00:17:05, but the condition is "the last N terminal events **in the lookback window** are all failures", and if dispatch stops no new terminal event arrives, so the same three failures remain the last three until the third-newest ages out.
The third-newest is at 2026-07-30 23:48:30.423, so the condition last holds at 2026-07-31 00:48:30 and abandon fires at **2026-07-31 01:48:30**, not 01:17:05.
§6.1:646's line "condition last holds 07-31 00:17:05" is false under §6.1's own §5.2.
The general bound is `last_failure + lookback` to `last_failure + 2*lookback` depending on the streak's internal span, not the flat one hour the spec asserts.
Round 3's "01:17:05 instead of 02:17:30" made the same conflation, and the fold copied it without re-deriving.

Open, intermittent holds: this is where the new defect lives.
§6.1:612-613 re-stamps the clock on every poll where "the condition" holds, and §5.2's condition is signature-agnostic ("share one signature", not "share the persisted signature").
§6.2:683 gives the state file three flat fields, so only one incident exists at a time, and §6.1:616 forbids a different-signature failure from re-opening.
Put together: an incident open on signature A, with a live outage now failing on signature B, is re-stamped every poll, never abandons, never closes, and never alerts for B.
That is the "held open forever, next real one deduped away" failure round 3's own component table says ABANDON exists to prevent.
It is inherited rather than introduced - round 2's "any non-`unknown` observation resets it" had the same hole, and no round has named it - but the fold restated the rule and did not close it.

The "written by a build without `last_failing_at`" case is vacuous for v1 (no build has shipped), but §6.1:614's claim that the elapsed test "never has a null to handle" is only true of files this build writes; `alerting.py:108-128`'s `_load` returns any dict it can parse, so a foreign file still needs a default.

VERDICT: FIX INTRODUCED A NEW DEFECT.
Two: the worked example is wrong by 31 minutes and rests on a false statement about when the condition stops holding, and the reframed clock's scope was never pinned to the persisted signature.

What to change: J1 and J4.

## Findings

**J1 - BLOCKER - the abandon clock is signature-agnostic, so a different-signature outage holds the first incident open forever and is never alerted.**
`docs/specs/992-session-fatal-probe-edge.md:612-613` re-stamps `last_failing_at` "on every poll where the condition holds"; §5.2:420-423 defines the condition as "share one signature", not the persisted one; `:616` forbids a different-signature failure from re-opening; §6.2:683 gives the file three flat fields, so one incident exists at a time.
Failure scenario: an incident opens on signature A, the operator fixes A, dispatch resumes and now fails on signature B three times an hour for six hours.
Every poll re-stamps A's clock, so A never abandons; no success exists, so A never closes; B cannot open.
Slack is silent for six hours while `session_health` publishes B's error to a heartbeat key nothing reads (§4.4:319-326).
This is inherited from round 2's "any non-`unknown` observation resets it" and no round has named it, but the fold restated the rule and did not scope it.
Fix: make the clock read "the condition has not held **with the persisted signature** for a full lookback", say explicitly what happens when the condition holds with a different signature while an incident is open (abandon the old one and open the new one is the only outcome that preserves the spec's own purpose), and add it as a test-15 parametrization.

**J2 - MAJOR - "every reap orphan carries exactly this one string" is false; a third close path writes a different byte-identical string, and §2.2 contradicts §2.3.**
Spec `:131`. `bobi/reconcile.py:200-208` writes `error=f"agent exceeded its {entry.timeout}s timeout without reporting a terminal status"` on an active entry whose deadline has passed and whose pid is alive **or zero**, the pid-0 case `is_dead_run` cannot see (`bobi/reconcile.py:109-111`, `bobi/sdk.py:588-591`) and which `bobi/subagent.py:1610-1615` documents as the restart-orphan close path.
Failure scenario: a manager restart lands while three sibling runs of one workflow sit registered `starting` with pid 0 (`subagent.py:1506` registers with no `pid`; the stamp is at `:1640`); the next `reconcile_sessions` at manager start (`bobi/service.py:742-744`) closes all three in one sweep with one byte-identical string, `terminal_at` within milliseconds, and the detector opens an incident on a pure restart artefact - the exact false positive the name exclusion exists to kill.
Measured: the registry holds the 2-member instance at 2026-08-20 17:11:36 / 17:11:39 (`timeout=3600`, `reconciled_at` set, byte-identical), 7 minutes from a `DIED_WITHOUT_TERMINAL` pair in the same orphan event, and the spec's own §2.3:163 shows that pair opening a second incident at N=2 without connecting it to §2.2.
Fix: restate `:131` as "both *dead-pid* reap sites carry this one string", add `reconcile.py:200-208` to §2.2's inventory, add the timeout signature to §2.2's table (n=2), and either exclude the timeout sentinel by name alongside `DIED_WITHOUT_TERMINAL` or state in §5.2 that the pid-0 restart-orphan sub-case is an accepted false positive - §6.3:708-712 accepts only the "three long runs genuinely past deadline" sub-case, which is a different thing.

**J3 - MAJOR - "empty is not a signature" is insufficient; `turn failed (kind=unknown, api_status=None)` is a second degenerate signature with 154 live instances.**
Spec `:441-449` guards a degeneracy with 0 of 65 instances and leaves unguarded the one with 24 of 65.
`bobi/brain/base.py:186-187` is the last resort of the one shared composition, returning a single byte-identical string whenever `error_message` and `result_text` are both empty - that is, precisely when the cause is unknown.
Failure scenario: three unrelated turn failures with no `error_kind` and no `api_error_status` land inside one hour; they share the signature exactly, the condition holds, and the alert posts "the last 3 sessions all reached a terminal failure with the same error" quoting `turn failed (kind=unknown, api_status=None)` - a string with no operator action, from three different causes.
Measured: 154 registry-wide (129 on `status="error"`, 24 on failed/crashed), one distinct raw string, spanning 2026-08-04 to 2026-10-01; latent only because the smallest 3-span is 86338s.
§5.3:522 already names this as "a 154-entry recurring cluster" and uses its size as the reason to keep `status="error"` out of the candidate set.
Fix: add it to §5.2's not-a-signature list by its own named constant alongside `DIED_WITHOUT_TERMINAL`, and parametrize test 9 with it.

**J4 - MAJOR - §6.1's abandon walk is wrong by 31 minutes, and the claim it rests on is false.**
Spec `:643-649`. The last session-limit failure is at 00:17:05, but the condition keeps holding until the third-newest ages out of the lookback, which is 2026-07-30 23:48:30.423 + 3600 = **2026-07-31 00:48:30**, so abandon fires at **01:48:30**, not 01:17:05.
Failure scenario: a Gate-1 reader or an implementor takes `:646` ("condition last holds 07-31 00:17:05") as a statement about the condition and sizes the abandon latency at one lookback; it is actually between one and two lookbacks after the last failure, depending on the streak's internal span, which is unbounded in the N=3 definition.
Fix: correct the two lines to 00:48:30 and 01:48:30, and add one sentence stating the general bound - abandon lands `lookback` to `2*lookback` after the last failure, because the streak itself has to age out before the clock starts.

**J5 - MAJOR - §5.2's stated give-up is narrower than the real one; a brain-fatal cause can reach `DIED_WITHOUT_TERMINAL`.**
Spec `:133` ("never the brain-fatal shape") and `:435-440` (the give-up is "an OOM or a SIGKILL... a host condition").
`bobi/manager_health.py:139` publishes the director's registry status verbatim as `/health`'s `manager.status`; `bobi/session.py:990-995` sets `status="error"` on exactly `ERROR_KIND_AUTHENTICATION` / `ERROR_KIND_CREDITS_EXHAUSTED`; `bobi/supervisor/supervision.py:68` and `:740-745` restart the manager on that status with no debounce.
Failure scenario: the credential dies, a director turn classifies it, `/health` reports `manager.status="error"`, the supervisor restarts the manager, every in-flight dispatch is orphaned into `DIED_WITHOUT_TERMINAL`, and the detector reads healthy on a genuinely brain-fatal cause.
The spec scopes that hazard out in §9:818-823 but never connects it to §5.2's give-up, so §5.2 reads as if only host conditions land there.
Fix: add the DEAD_STATES path to `:435-440`'s give-up by name, and soften `:133` to "the orphan shape, which a brain-fatal cause reaches only through the DEAD_STATES restart that §9 scopes out".

**J6 - MAJOR - "M is a 4-file saving" is stale after the D5 scope cut, and Q1 misattributes it.**
Spec `:300` and `:944` both say 4; `:303-305` enumerates three files plus one test *item*; `:793` correctly enumerates the three (`snapshot.py`, `supervision.py`, `ADMIN_PROTOCOL.md`) plus test 10.
The 4 came from round 3's 11-file count, where the fourth was `tests/test_supervision.py` - which D5 removed from the R scope entirely, so it can no longer come off for M.
Failure scenario: Gate 1 rules on Q1, the one blocking question, weighing M at a 4-file saving against R when it is a 3-file saving; the number is the whole M-vs-R trade and the spec states it twice, both times wrong.
Q1:942-944 also says both non-surviving claims are "in §4.4", but §4.4's two bullets are "R's block is read by nothing" and "R's one concrete gain is the admin surface"; the 4-file claim lives in §4.3.
Fix: 3 files plus test 10 in both `:300` and `:944`, and re-point Q1 at §4.3 for the M arithmetic.

**J7 - MINOR - the kill switch has no test, and the file that would have supplied the pattern was dropped from scope.**
Spec §8:748-767 and §9:786-791. `tests/test_supervision.py:601-607` (`test_disabled_knob_bypasses_the_gate`) is load_grace's kill-switch test; §10's 16 items contain nothing equivalent, and test 16 runs with the feature enabled.
Failure scenario: `WATCHDOG_SESSION_FATAL_ENABLED=0` is wired to the detector but not to the alerter (or vice versa), ships, and an operator trying to silence a misbehaving reader finds it still posting.
Fix: add one item asserting that with the knob at 0 a holding fixture yields a null block and no Slack post - in `tests/test_supervisor_alerting.py` rather than reviving `tests/test_supervision.py`.

**J8 - MINOR - the bounded reader is untested, and its correctness rests on an invariant the spec never states.**
Spec §5.4:555-560. Filtering on `st_mtime >= now - lookback` is safe only because mtime is always >= `terminal_at`: `mark_terminal` writes both in one `update` (`bobi/sdk.py:552-567`, `:377-399`), so the mtime set is a superset of the in-window-terminal set.
Failure scenario: an implementor filters on mtime and then sorts or windows on mtime rather than re-filtering on `terminal_at`; `bobi/reconcile.py:184` writes `emit_confirmed=True` after `mark_terminal`, so a session that went terminal three hours ago can carry a five-minute-old mtime and enter the streak.
Fix: state the invariant in §5.4 and add one test item with a fixture whose mtime is inside the lookback and whose `terminal_at` is outside, asserting it does not count.

**J9 - MINOR - `since` is specified in detail and asserted by nothing.**
Spec §4.2:275-281 defines it as the oldest failure's `terminal_at` in the current streak, re-derived every poll, never a duration source, and quotes a 24.7-minute divergence from `opened_at` on the July incident (which I reproduce exactly: 22:39:35 against 23:04:15).
Tests 1 and 10 assert the block and the error; no item asserts `since`.
Failure scenario: `since` ships as `opened_at`, or as the newest rather than oldest streak entry, and the dashboard dates a two-hour condition as two minutes with no test failing.
Fix: extend test 1 to assert `since` against the July fixture's oldest streak `terminal_at`.

**J10 - MINOR - a fail-open null advances the abandon clock, and the spec never says so.**
Spec §7:737-739 yields a null on an unreadable registry; §6.1:609-613 abandons when "the condition has not held" for a lookback.

# Round-3 review: ask-first login-bootstrap spec

**Spec:** `plans/2026-10-09-login-bootstrap-ask-first.md` @ `7ba3c0cdf34f980a80d158776d4b7904c8af8610` (branch `agent/958`), 671 lines.
**Citation baseline read:** `origin/main` @ `83bebe49af55523dec7c587aedfd7f6cbd205343` (`/tmp/wt-958-main-r2`), which is the SHA the spec pins.
**Current main read:** `70db2e1059fdf8f35751b17806496cb91f427b09` (`/tmp/wt-r3-main`).

**Verdict: NOT READY.**

The round-2 folds are mostly correct and I reproduced their measurements: the 3b cleanup line at its new position after `:488` does fix the loop the round-1 position left behind, the four `auth.json` states behave as claimed in `api_key` mode, and the Q4 reversal to the directory shape is justified by the logout evidence.
The fold did not introduce a textual defect this round.
What it did not do is fix the class of defect, and two previously unmodelled axes break the spec's central verified claim.
The spec's harness recreates `$HOME` fresh on every simulated boot and invents a `/opt/bobi/skills`-derived entry inside `$HOME/.codex/skills`.
Neither matches the image or the machine: a same-machine restart keeps the overlay (the entrypoint says so itself at `:400-401`), and nothing in the build ever links `/opt/bobi/skills` into `~/.codex/skills`.
With the overlay persisted across a brain switch, 3c as written builds a silent self-referential symlink loop at `${CODEX_HOME}/skills` (R3-F1), and verification item 12's core assertion cannot pass on a real image (R3-F2).
Separately, the fold's new `codex_auth_is_oauth` predicate is a third competing definition of "usable codex credential" that pins a state the repo's own validator rejects (R3-F5), and the widened subscription sweep it adds to scope is a new destructive path with no verification item (R3-F4).
A simpler shape for section 3 exists, I built and tested it, and it removes R3-F1, R3-F2, R3-F3 and the entire boot-order matrix as a correctness requirement. See [the simplification question](#the-simplification-question-s4).

### R3-F1 (blocker): 3c builds a silent symlink loop when the container overlay persists across a brain switch

**What the spec claims.** Appendix A: "**The shape in 3.4 is correct on every boot order** | same 6 sequences, same harness: every boot exits 0, `readlink -f` resolves".

**Why the harness cannot see this.** `/tmp/h958.sh:12` does `rm -rf "$HOME"; mkdir -p "$HOME/.codex/skills"` at the top of every simulated boot, so `$HOME` is always a fresh image rootfs.
That models a `fly deploy`. It does not model a same-machine restart, and the entrypoint states the distinction itself at `docker/docker-entrypoint.sh:400-401`:

```
# (a fresh image rootfs each deploy ships the real dir; a same-machine restart
# already has the link).
```

**The failure.** `${HOME}/.codex` is written in exactly one place, `:527-531`, inside the codex-brain block. Nothing on a non-codex boot ever restores it to a real directory:

```
  527:  if [ "$(readlink "${BRAIN_HOME_LINK}" 2>/dev/null)" != "${BRAIN_CRED_DIR}" ]; then
  529:    rm -rf "${BRAIN_HOME_LINK}"
  530:    ln -s "${BRAIN_CRED_DIR}" "${BRAIN_HOME_LINK}"
```

So on a rootfs that has booted codex once, `$HOME/.codex` is a symlink to `${DATA_DIR}/codex` forever.
3c then evaluates `ln -sT "${HOME}/.codex/skills" "${DATA_DIR}/codex/skills"` as a link to itself.

Measured, with the real entrypoint text and the cleanup line at `:488`:

```
--- O2-baseline (spec shape), HOME PERSISTED, baked=yes ---
SEQ=claude,codex,claude
boot1 claude rc=0 kind=symlink readlink_rc=0 list="baked-a gstack-browse "
boot2 codex  rc=0 kind=realdir readlink_rc=0 list="baked-a "
boot3 claude rc=0 kind=symlink readlink_rc=1 list="/tmp/.../data/codex/skills "
SEQ=codex,claude,codex
boot1 codex  rc=0 kind=realdir readlink_rc=0 list="baked-a "
boot2 claude rc=0 kind=symlink readlink_rc=1 list="/tmp/.../data/codex/skills "
boot3 codex  rc=0 kind=realdir readlink_rc=0 list="baked-a "
```

Direct inspection of the boot-3 tree:

```
$HOME/.codex          -> /tmp/.../data/codex
/data/codex/skills    -> /tmp/.../home/.codex/skills
readlink -f /data/codex/skills  ->  rc=1
```

rc=0, no log line. This is the "SKILLS LOST" class the spec itself calls "a strictly worse failure than the abort it replaced, because nothing reports it", and on a claude brain it never self-heals: every subsequent claude boot `rm -rf`s the link and recreates the same loop.

**Reachability.** The brain is resolved from the installed team's `agent.yaml` on the volume when `BOBI_BRAIN` is unset (`:276-278`: `if [ -z "${BOBI_BRAIN:-}" ] && [ -n "${configured_brain}" ]; then ENTRYPOINT_BRAIN="${configured_brain}"`).
So editing `brain.kind` on the volume and restarting the machine switches the brain with no new rootfs. That is within the spec's own stated threat model ("the volume outlives the brain choice").

**Blast radius.** I confirmed `codex exec` tolerates a looped `${CODEX_HOME}/skills` (same 401 as a clean run, no crash), so the cost is silent loss of codex's skills including the `skills/.system` tree it manages itself, not a boot abort.

**Fix.** Preferred: take the simpler shape in [S4](#the-simplification-question-s4), which creates no `${DATA_DIR}/codex/skills` object at all and is clean on this axis (measured below).
If 3c keeps the link, it needs the mirror of 3b's cleanup line, repairing a stale brain link before using it as a link target:

```sh
if [ "${ENTRYPOINT_ENGINE}" != "codex" ]; then
  # A previous codex boot on this same rootfs left ~/.codex as a link to the
  # volume; using it as a link target here closes a loop on ${DATA_DIR}/codex.
  [ -L "${HOME}/.codex" ] && rm -f "${HOME}/.codex"
  mkdir -p "${HOME}/.codex/skills"
  rm -rf "${DATA_DIR}/codex/skills"
  ln -sT "${HOME}/.codex/skills" "${DATA_DIR}/codex/skills"
fi
```

Either way, verification item 12 must gain a persisted-`$HOME` axis, and the harness must stop recreating `$HOME` per boot.

### R3-F2 (major): verification item 12's core assertion cannot pass on a real image

**The claim.** Item 12: "on each non-codex boot `$CODEX_HOME/skills` resolves and lists **both** a baked and a tool-installed skill".
Appendix A's `OK` oracle: "every non-codex boot lists both `baked-a` and `gstack-browse`".
3c's own comment: "any other brain needs a link out to the image's own codex skills".

**Nothing puts a `/opt/bobi/skills` entry into `~/.codex/skills`.** The build renderer links `BAKED_SKILLS` into `~/.claude/skills` and nowhere else (`bobi/build_render.py:220-221`):

```
220: f"install -d -o {APP_USER} -g {APP_USER} {BAKED_SKILLS}",
221: f"{as_user} ... 'mkdir -p ~/.claude && rm -rf ~/.claude/skills && ln -sfn {BAKED_SKILLS} ~/.claude/skills'",
```

`grep -rn 'BAKED_SKILLS' bobi/ hatch_build.py Dockerfile` returns only `build_render.py`, and `grep -n '/opt/bobi/skills' Dockerfile` returns nothing.
On the live eng-team image:

```
$ readlink ~/.claude/skills            -> /opt/bobi/skills
$ ls -A ~/.codex/skills | wc -l        -> 50
$ find ~/.codex/skills -maxdepth 1 -lname '/opt/bobi/skills*' | wc -l   -> 0
```

Every `~/.codex/skills` entry points into `/home/bobi/dev/gstack/.agents/skills/`, i.e. the gstack tool installer's own population (`bobi/tool_library/gstack/tool.yaml:35`).
The `baked-a` entry the harness planted at `/tmp/h958.sh:13` (`ln -sfnT "$ROOT/opt/bobi/skills/baked-a" "$HOME/.codex/skills/baked-a"`) has no counterpart in any build step.

**Consequences.** Two, both real.
Item 12 as written is a test that fails on a correct implementation, so it would be weakened or deleted during implementation, taking the shape's only guard with it.
And 3c's stated purpose is overstated: on a non-codex brain the link exposes only the tool-installer population, never the baked team skills, which reach `~/.claude/skills` instead.

**Fix.** Either drop the link (S4), or correct item 12 to "lists the tool-installer population (`gstack-browse`)" and correct 3c's comment and the Appendix A oracle to match. Do not assert a baked `/opt/bobi/skills` entry under `~/.codex/skills`; add one in the build first if that is actually wanted.

### R3-F3 (major): `readlink -f` passes on a dangling link, so item 12's assertion is blind

The spec uses "`readlink -f` resolves" as its correctness oracle throughout Appendix A, and item 12 asserts "`rc=0` and no symlink loop" for the `/opt/bobi/skills`-absent axis.
`readlink -f` permits the final component to be missing; only `readlink -e` requires it to exist.

Measured with the spec's shape and `${HOME}/.codex/skills` absent (a generic image: no build `run:` steps, so no gstack installer and no `~/.codex/skills`):

```
BAKED=yes SEQ=claude
boot1 claude rc=0 kind=symlink readlink_rc=0 list="/tmp/.../data/codex/skills "

$ readlink /data/codex/skills     -> /tmp/.../home/.codex/skills
$ readlink -f /data/codex/skills  -> /tmp/.../home/.codex/skills   rc=0
$ readlink -e /data/codex/skills  ->                               rc=1
```

So `${CODEX_HOME}/skills` is broken, item 12's two assertions both pass, and `readlink -f` reports success. `codex exec` through it is silent (measured: identical 401, no `skills/.system` created).

**Fix.** Change the oracle to `readlink -e` or `[ -d "${CODEX_HOME}/skills" ]` in item 12, item 14 ("`readlink -f` on the skills path exits 0") and Appendix A. Add the `${HOME}/.codex/skills`-absent axis, which is a third axis the spec does not have, or remove the link (S4).

### R3-F4 (major): the widened subscription sweep is a new destructive path with no verification item

§3.4 adds to scope "Widen its predicate the same way: the sweep should remove any `auth.json` that is not usable OAuth", and §6 lists "a widened sweep predicate".
Verification item 11 is explicitly `api_key`-only: "Four states of `${CODEX_HOME}/auth.json` under `BOBI_AUTH=api_key` with `OPENAI_API_KEY` set".
No item covers the sweep in subscription mode, which is the mode eng-team runs (Appendix A "Live env") and the mode in which the sweep is the only arm that executes.

The widening is not cosmetic: it inverts the sweep's failure mode from conservative to destructive.
`codex_auth_uses_api_key` exits 1 on anything it cannot classify (`:344-347`), so today an unrecognised file is never deleted. Under `! codex_auth_is_oauth` an unrecognised file is deleted on every boot. Measured:

```
############ MODE=subscription (WIDENED sweep) ############
absent               rc=0  UNCHANGED  after=<none>      log: removing Codex API-key auth file so OAuth can be used
apikey               rc=0  CHANGED    after=<none>      log: removing Codex API-key auth file so OAuth can be used
oauth                rc=0  UNCHANGED  after={...tokens...}
truncated            rc=0  CHANGED    after=<none>      log: removing Codex API-key auth file so OAuth can be used
oauth_blank_refresh  rc=0  UNCHANGED  after={"tokens":{"refresh_token":""}}
```

The spec also flags in "Could not verify" that codex's `--device-auth` write path was never observed. A destructive predicate keyed on an unobserved file shape, acting on the one credential this feature exists to create, needs a test.

**Fix.** Extend item 11 to both modes over the same state set, and add an explicit leg: "a valid OAuth file survives a subscription boot". State in item 11 that the subscription leg is the one that deletes.

### R3-F5 (major): `codex_auth_is_oauth` is a third definition of "usable codex credential", and it pins a state the repo's own validator rejects

The repo already has one authority on this question, `subscription_credentials_status(path, "codex")` (`bobi/auth_bootstrap.py:162-171`), reachable from shell as `python -m bobi.auth_bootstrap credential-status codex <path>` and already called from this very script at `:570-571`.
The fold adds a second shell predicate that tests only `data.get("tokens")` truthiness. The two disagree:

```
$ python -m bobi.auth_bootstrap credential-status codex <file>
oauth    rc=0  credentials valid: refresh token is present
apikey   rc=1  credentials invalid: tokens is missing or malformed
trunc    rc=1  credentials invalid: credential JSON is malformed
blank    rc=1  credentials invalid: refresh token is missing or blank
missing  rc=1  credentials invalid: credential file is missing
```

`{"tokens":{"refresh_token":""}}` is `invalid` to the validator and `is_oauth` to the new predicate. Measured consequence with the spec's predicate:

```
MODE=api_key       oauth_blank_refresh  UNCHANGED  (materialization permanently refused)
MODE=subscription  oauth_blank_refresh  UNCHANGED  (sweep permanently refuses to clear it)
```

So the state survives both arms, and in `api_key` mode the team is wedged with no working credential, which is the exact failure mode the spec says the positive predicate exists to prevent ("Asserting `tokens` instead sends every non-OAuth state (absent, api-key, garbage) down the materialize path, which is the recovery"). That enumeration is incomplete: it omits OAuth-shaped-but-unusable.

Replacing the predicate with the existing validator fixes all five states. Measured against my harness:

```
MODE=api_key       absent/apikey/trunc/blank -> replaced ; oauth -> preserved + log
MODE=subscription  apikey/trunc/blank -> removed ; oauth -> preserved ; absent -> no-op
```

**Fix.** Delete `codex_auth_is_oauth`. Use `as_app python -m bobi.auth_bootstrap credential-status codex "${CODEX_HOME}/auth.json"` in the non-clobber guard and `! ...` in the sweep. `/opt/venv/bin` is on `PATH` for root via the Dockerfile `ENV` at `:142`, so this works in both the root section and under `as_app`. One code path for "is this codex credential usable", which is the standing bar; also removes ~14 lines and a heredoc.

### R3-F6 (major): "subscription mode self-heals regardless" is false on the arm the paragraph is about

§3.4: "Severity, stated accurately: subscription mode self-heals regardless, because section 4's `credential-status` check (`:570-571`) reports the file invalid and `login-bootstrap` re-mints over it."

Section 4 checks the brain's credential, not codex's:

```
569:   credential_path="${BRAIN_CRED_DIR}/${BRAIN_CRED_FILE}"
570:   if credential_reason="$(as_app python -m bobi.auth_bootstrap \
571:       credential-status "${ENTRYPOINT_ENGINE}" "${credential_path}" 2>&1)"; then
575:     as_app bobi agent "${AGENT_NAME}" login-bootstrap
```

On a claude brain `BRAIN_CRED_DIR="${CLAUDE_CONFIG_DIR}"` and `BRAIN_CRED_FILE=".credentials.json"` (`:100-102`), and `:575` is bare so it logs in the brain only.
The paragraph is specifically about the non-codex arm (`:546-548`), i.e. a claude brain, where section 4 never looks at `/data/codex/auth.json`.
There is no boot-time self-heal for the codex tool credential. Recovery requires a worker 401, a director dispatch and a human reply.

**Fix.** Restate as: "in subscription mode the widened sweep is the boot-time recovery; section 4 does not see the tool credential on a non-codex brain, so without the sweep there is no boot-time recovery in either mode." That also makes R3-F4's missing test obviously necessary.

### R3-F7 (major): verification item 4's four-leg table is wrong about the adapter and would drive a Z5 violation

The table asserts `fields.thread_ts` is **absent** for `slack.mention` and for `slack.dm`, and that both are therefore "not ready".

`threadTs` is read once, before any type branching, and applied to every emitted type:

```
chat-sdk-slack.ts:106   const threadTs = (innerEvent.thread_ts as string) || "";
chat-sdk-slack.ts:115   if (eventType === "app_mention") {
chat-sdk-slack.ts:116     slackEventType = "slack.mention";
chat-sdk-slack.ts:166   if (threadTs) fields.thread_ts = threadTs;
```

A human who @mentions the bot **inside the ask's thread** produces `app_mention` with `thread_ts` set, takes the `:115-116` branch before the dedup branch at `:117-118`, and is emitted as `slack.mention` carrying `fields.thread_ts == <the ask's ts>`.
Per 3.2(d) ("the thread condition is `fields.thread_ts == <the ask's ts>`") that event **is** ready, and per Z5 it must be. The table says no.
A DM thread reply likewise takes `:119-120` and carries `fields.thread_ts`.

This is the defect path: an implementer writing item 4 from the table builds a `slack.mention` event, finds the `fields.thread_ts`-only predicate accepts it, and "fixes" the predicate by adding an event-type filter. That rejects a human message in the ask's own thread, which Z5 forbids.

The `slack.dm` row is also dead. `_extract_code`'s login-channel check compares channel ids and drops a DM before any thread test:

```
496:     ev_channel = fields.get("channel") or payload.get("channel")
498:     if expected_channel and ev_channel and ev_channel != expected_channel:
499:         return None
```

`fields.channel` is Slack's raw id (`:129` -> `:162`), and the login channel resolves to a `C…` id (`bobi/auth_bootstrap.py:297`, `:302`), so a `D…` DM never passes. On the conversation-ref path a DM's conversation is `slack:T…:dm:D…:thread:…`, which fails `_conversation_matches` at `:488-491`.

**Fix.** Replace rows 3 and 4 with:

| Event | `fields.thread_ts` | Ready? |
|---|---|---|
| `slack.thread_reply` in the ask's thread | the ask's `ts` | yes |
| `slack.thread_reply` in another thread | another `ts` | no |
| `slack.mention`, top-level in the login channel | absent | no |
| `slack.mention`, **inside the ask's thread** | the ask's `ts` | **yes (Z5)** |

Drop the `slack.dm` row, or keep it with the note that it is unreachable past `:498-499` for a channel-configured login.
Also correct 3.2(d)'s supporting sentence, which currently says `app_mention` "does not require `threadTs`" in a way that reads as "never has it".

### R3-F8 (major): the prescribed `tool.yaml` fix re-opens the credential clobber the entrypoint guard just closed

§3.4 says `bobi/tool_library/codex/tool.yaml` must "honour `CODEX_HOME`", and notes that `success:` "also *writes* in its `elif` branch ... so it would additionally create an api-key file where codex never looks".
The write is unguarded. From `tool_library/codex/tool.yaml:6`:

```
elif [ "${BOBI_AUTH:-api_key}" != "subscription" ] && [ -n "${OPENAI_API_KEY:-}" ]; then
  mkdir -p ~/.codex && python3 -c 'import json, os, pathlib; p=pathlib.Path.home()/".codex"/"auth.json"; p.write_text(json.dumps({"OPENAI_API_KEY": os.environ["OPENAI_API_KEY"]})+"\n"); p.chmod(0o600)'
```

After the prescribed retarget this writes `${CODEX_HOME}/auth.json`, unconditionally, every time the preflight runs, in `api_key` mode with `OPENAI_API_KEY` set. That overwrites the human-minted OAuth credential on the durable volume, with none of the non-clobber protection §3.4 just spent a page adding to `:547`.
The spec frames the write as a problem only in the "don't honour `CODEX_HOME`" direction, so an implementer following §3.4 ships the clobber.

**Fix.** State that the `tool.yaml` change is a retarget **plus** the same guard: the `elif` must not write when a usable OAuth credential already exists at `${CODEX_HOME}/auth.json`. The cheapest form reuses the same validator as R3-F5.
Also add `bobi/tool_library/codex/guide.md:42` to scope, which states "materializes `~/.codex/auth.json` from `OPENAI_API_KEY` before launch" and becomes wrong under the export.

### R3-F9 (minor): the widened sweep logs a credential deletion that did not happen

With no `auth.json` at all, `codex_auth_is_oauth` exits 1 (the `except` at `:346-347` catches `FileNotFoundError`), so the negated sweep enters and logs. Measured:

```
MODE=subscription  absent  rc=0  UNCHANGED  after=<none>
      log: [entrypoint] Subscription mode: removing Codex API-key auth file so OAuth can be used
```

That fires on every boot of every subscription-mode machine with no codex credential yet, which is every machine before the first login. It destroys the log line's value as the audit signal that a credential was deleted.

**Fix.** `if [ -f "${codex_dir}/auth.json" ] && ! <validator> "${codex_dir}/auth.json"; then`. Verified clean in my O2 harness: `absent` produces no sweep log.

### R3-F10 (minor): Q1 Option C's two `ts` slots are the same directory on a codex brain

Q1 Option C: "`${DATA_DIR}/codex` for a tool and the brain credential dir for the brain, named by path rather than by `${CODEX_HOME}` so it holds under either Q4 shape."

On a codex brain the brain credential dir **is** `${DATA_DIR}/codex` (`:89`: `BRAIN_CRED_DIR="${DATA_DIR}/codex"`). So the brain's stored ask `ts` and the codex tool's stored ask `ts` collide at one path, and the invalidation rule ("clear the stored `ts` once the login succeeds") would clear the other flow's ask.
On a claude brain the brain slot is `${CLAUDE_CONFIG_DIR}` (`:31`, default `${DATA_DIR}/claude`), which is Claude's own managed config dir.

Confirmed sound: `rm -rf "${DATA_DIR}/codex/skills"` does not touch a `ts` stored at `${DATA_DIR}/codex/<file>`, so that seam is fine.

**Fix.** One location, filename keyed by target: `${DATA_DIR}/codex/.login-ask-<target>` or a single `${BOBI_HOME}/login-ask-<target>.ts`. Say it in Q1 so the collision is not discovered at implementation.

## The simplification question (S4)

**Yes, a simpler shape exists, and it is strictly better. Drop the `${DATA_DIR}/codex/skills` link entirely.**

Section 3's whole defect history comes from one decision: `${DATA_DIR}/codex/skills` must be a *different kind of object* depending on the brain, while both brains write to it on the same persistent volume.
Every bug has been an instance of that: the abort (`ln` over a directory), the silent skills loss (skip-if-present inheriting the wrong kind), the symlink loop (link target repointed under it), R3-F1 (link target repointed on a persisted overlay), R3-F3 (link target absent).
Patching instances cannot end, because the collision is the design.

### The shape

```sh
# --- 3c. Codex's durable config dir, both brains (#958) ---------------------
# On a codex BRAIN this is already ~/.codex via 3b; the export just names the
# same directory. On any other brain it moves codex's config dir onto the
# volume so a human-minted auth.json survives a roll. No `skills` object is
# created here: nothing in the tree reads ${CODEX_HOME}/skills, and codex
# materializes its own skills/.system on first invocation.
mkdir -p "${DATA_DIR}/codex"
chown "${APP_USER}:${APP_USER}" "${DATA_DIR}/codex"
export CODEX_HOME="${DATA_DIR}/codex"
```

Three statements, no branch, no `ln`, no `rm -rf`. 3b is left **completely untouched** (no cleanup line, so no placement analysis, no `[ -d /opt/bobi/skills ]` interaction, no errexit-position argument). Combined with R3-F5's validator reuse, section 3's entrypoint delta is 3 new lines plus 2 changed lines, against ~36 for the spec's shape.

### Why dropping the link is safe

Nothing in the tree reads `${CODEX_HOME}/skills`:

```
$ grep -rn 'codex_home()' --include=*.py .
bobi/brain/codex.py:387, bobi/brain/codex_config.py:51,181,208, bobi/chat_history.py:317, bobi/brain/instructions.py:123
$ grep -rn -A2 -B2 'codex_home()' --include=*.py . | grep -i skills
(no hits)
```

The only in-repo references to `~/.codex/skills` are gstack's installer (`tool_library/gstack/tool.yaml:33`, `:35`, `:51`), and all three are `rm -rf`/absence assertions against `$HOME/.codex/skills` by literal path, which the export does not move.
codex builds `skills/.system` itself: a single `codex exec` into a fresh `CODEX_HOME` created it (measured above), so on a claude-brained machine `${CODEX_HOME}/skills` appears on first use, on the volume, durable.

### What it costs

On a claude-brained machine that has never booted codex, `codex exec` no longer sees the gstack skills that the tool installer put in `$HOME/.codex/skills`.
That is the entire loss, and it is small: those entries are a side effect of gstack's installer (which also deliberately prunes six of its own codex-side skills at `tool.yaml:51`), nothing in the fleet requires them, and codex's role in #958 is adversarial second opinion via `codex exec`, not skill dispatch.
Per R3-F2 the baked team skills never reached `~/.codex/skills` anyway, so the link was never delivering what 3c's comment claims it delivers.
A bonus falls out: after any codex boot, `${CODEX_HOME}/skills` holds 3b's real links into `/opt/bobi/skills`, and a later claude boot **keeps** them instead of `rm -rf`ing them, so codex-on-a-claude-brain ends up with *more* skills than under the spec's shape.

### What it deletes from the spec

- the `!= "codex"` gate and its justification
- `rm -rf "${DATA_DIR}/codex/skills"` and the whole "cost of `rm -rf`" subsection, including the brain-switch data-loss trade and the `codex exec` writes `skills/.system` caveat
- the 3b cleanup line, its placement analysis, the `:488` vs `:491` argument, and the errexit-position paragraph
- the three-shape boot-order matrix table as a correctness requirement
- verification item 12 shrinks to "every boot exits 0"; item 13's and item 14's skills assertions go away
- R3-F1, R3-F2 and R3-F3 become impossible rather than fixed
- Q4's "both round-1 blockers on the skills link" argument becomes moot for the directory shape too, which strengthens the Q4 recommendation rather than weakening it

### Candidates ruled out, and why

- **A single idempotent `ensure_codex_links()` called from one place.** Does not remove the class: the path still has to be two kinds of object. Worse, the spec's own measurement shows the bare `[ -L x ] && rm -f x` form exits 1 as a function body's last command under errexit, so moving the logic into a function adds a new abort mode.
- **Make 3c unconditional by choosing a non-colliding path, e.g. `CODEX_HOME=${DATA_DIR}/codex-tool` on a non-codex brain.** Works, but introduces a second durable credential location, makes `:544` and `:547` write different paths, splits Q1's stored `ts` across two homes, and leaves the credential behind on a brain switch. Strictly more moving parts than deleting the link.
- **Export `CODEX_HOME` to the credential's parent only.** That *is* `${DATA_DIR}/codex`; there is no narrower directory. The file-level variant is Q4's rejected shape, already ruled out on the logout evidence.
- **Do the link work at image build.** Impossible: `/data` does not exist at build time, which is why `build_render.py` bakes to `/opt/bobi/skills` instead.
- **Reorder 3c relative to the brain blocks so the cleanup line is unnecessary.** No ordering helps. The collision is on a *persistent* path across *boots*, not within one boot; the before-placement loops and the after-placement aborts, both already measured by the spec.
- **Make the export conditional on a non-codex brain.** Technically fine (`${CODEX_HOME}` is consumed only in the non-codex arms at `:547` and `:557`), and on a codex brain the export is already a no-op because `~/.codex` *is* `${DATA_DIR}/codex`. But it buys nothing and couples two distant code sites under `set -u`. Keep the export unconditional.

### Recommendation

Take the three-line 3c above, leave 3b untouched, and reuse `credential-status` for both predicates (R3-F5).
Keep everything else in §3.4: the placement interval between `:532` and `:538` is still required (both retargets consume `${CODEX_HOME}`), both retargets are still required, and the non-clobber guard is still required.

## Findings

1. **F1 — High: degraded detection still unsubscribes the real topic.**  
   [subagent.py:2114](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/subagent.py:2114) guards only when `set(desired) < set(previous)`. If a Slack-only team’s detector fails, [subscriptions.py:244](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/events/subscriptions.py:244) returns `[project_path.name]`. The new desired set replaces `slack:T1...` with the fallback topic, so it is not a subset and the reconnect PUT drops Slack routing. The test at [test_subscription_reload.py:345](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/tests/test_subscription_reload.py:345) simulates a pack list shrinking, not the detector’s actual fallback behavior.

2. **F2 — High/security: the token is briefly, and potentially permanently, world-readable.**  
   [manager_health.py:330](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/manager_health.py:330) uses `write_secret`, which creates the file with `write_text` and only afterwards calls `chmod(0600)` at [launcher.py:71](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/webui_common/launcher.py:71). On a normal `022` umask, a fresh token initially has mode `0644`. Another local process can read it in that window; SIGKILL or a failed `chmod` leaves it readable permanently. Here the token is the primary protection for a server that may bind `0.0.0.0`, unlike the local UIs for which this helper was written. The test checks only the eventual mode.

3. **F3 — High: live reload cannot recover failed Slack/WhatsApp/Discord registration.**  
   Boot and saved-deployment sync call `_register_channel_credentials` before authorization at [subagent.py:1926](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/subagent.py:1926) and [subagent.py:2002](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/subagent.py:2002). Reload instead calls only `authorize_resources` at [subagent.py:2135](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/subagent.py:2135). For these channel types, `authorize_resources` assumes their grants were written by registration; `None` means “registration was not attempted” and the topic is retained ([server.py:716](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/events/server.py:716)). Concrete case: channel registration transiently fails at boot while that topic is not yet declared; later `subscriptions add whatsapp:<id>` always gets a server rejection, and rerunning never retries registration. Only restart repairs it, contrary to the CLI guidance.

4. **F4 — High/concurrency: the advertised timeout excludes time waiting for the apply lock.**  
   Every reload waits at [subagent.py:1760](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/subagent.py:1760), but [cli.py:3311](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/cli.py:3311) budgets only one authorization-plus-PUT. Example: reload A is authorizing six GitHub topics, while reload B removes all topics. B gets a 40-second timeout because its final list is empty, despite first waiting up to roughly 70 seconds for A and then doing its own PUT. The CLI catches the timeout, reports “manager is not running,” and exits zero; B’s handler can subsequently acquire the lock and apply the removal. This directly contradicts the comment that the caller cannot give up before an apply lands. The concurrent tests use immediate mock/localhost responses and do not cover queued worst-case latency.

5. **F5 — Medium: the “strict” YAML validator accepts duplicate `subscribe:` keys.**  
   [subscriptions.py:117](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/events/subscriptions.py:117) uses default `yaml.safe_load`, which silently keeps the last duplicate mapping key. This file is therefore accepted:

   ```yaml
   subscribe:
     - github:o/keep
   subscribe: []
   ```

   It becomes authoritative `[]` and silently unsubscribes everything. The invalid-document matrix at [test_workspace_subscriptions.py:36](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/tests/test_workspace_subscriptions.py:36) checks duplicate list items, not duplicate mapping keys.

6. **F6 — Medium/concurrency: an invalid workspace file can still fall through to auto-detection.**  
   `discover_subscriptions` reads the workspace file at [subscriptions.py:221](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/events/subscriptions.py:221), then calls `explicit_subscriptions`, which reads it again. If the first read sees no file and a hand edit installs an invalid file before the second read, `WorkspaceSubscriptionsError` is swallowed by the broad `except Exception` at [subscriptions.py:225](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/events/subscriptions.py:225). The apply then auto-detects and PUTs instead of failing closed. Existing tests place the invalid file before both reads, so they miss the TOCTOU case.

7. **F7 — Medium: first-edit seeding can write a file that its own reader rejects.**  
   [cli.py:3460](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/cli.py:3460) validates command arguments but never validates topics copied from pack discovery before rendering them. A pack containing duplicate topics, or `inbox/worker-1`, is tolerated by the permissive pack parser. The first `subscriptions add` copies that list into `workspace/subscriptions.yaml`; the subsequent manager reload rejects the newly written file as invalid. The CLI cannot remove the forbidden topic because its argument validator rejects it. The round-trip test at [test_subscriptions_cli.py:100](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/tests/test_subscriptions_cli.py:100) uses only a valid seed.

8. **F8 — Medium: port/token-file presence is not a liveness test.**  
   [cli.py:3316](/data/.bobi/agents/eng-team/run/worktrees/952-subscriptions/bobi/cli.py:3316) treats both files as proof of a live manager, but they are removed only by graceful `stop()`. SIGKILL, OOM, or host loss leaves both behind. If the port is later reused by another local service or another team, the CLI sends the old secret to that process and can report a false 401 or interpret an unrelated response. At minimum the endpoint needs an authenticated identity/health probe before being called “self-evidencing.”

I did not run the test suite; this worktree has no `.venv`, and the system Python lacks PyYAML.

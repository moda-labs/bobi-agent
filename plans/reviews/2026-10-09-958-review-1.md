## Findings

### F1 - blocker - Section 3c's fix needs BOTH halves; the `[ -e ]` guard alone converts a loud abort into a silent capability loss

**Claim (§3.4):** "With the `[ -e ]` guard **and** the after-placement, both brains boot clean and the link resolves, idempotently across two boots." The table lists results for `brain=claude` and `brain=codex` *separately*, never a switch on one volume.

**What I ran.** A harness (`/tmp/bswitch.sh`) replaying entrypoint `:486-532` (the codex-brain block) plus the proposed 3c verbatim, booting twice on one persisted `$DATA_DIR` with a fresh `$HOME` each boot (the real container overlay resets `~` per boot; only `/data` persists).

```
### A. claude-then-codex, NO FIX (reproduces the established blocker)
brain=claude rc=0  skills->/tmp/bs-a/home/.codex/skills  baked_reachable=[baked-a]
brain=codex  rc=1  skills->ELOOP/MISSING  baked_reachable=[(empty)]
             ln: failed to create symbolic link '/tmp/bs-a/data/codex/skills': File exists
```

Two corrections to the established write-up:

1. **The failing `ln` is 3c's own `ln -sT`, not entrypoint `:524`.** `:524` is `ln -sfnT "${skill_path}" "${skill_dest}"` - it has `-f` and cannot fail this way. The abort comes from 3c's unforced `ln -sT` hitting a path that `[ -e ]` reported absent because `-e` on a looping symlink returns false (ELOOP). The guard *causes* the abort rather than preventing it.
2. **Fixing only 3c is worse than the abort.** I patched 3c to assert its shape (`rm -rf` + `ln -sT`, gated on a non-codex brain) and left the codex block alone:

```
### new 3c only, no codex-block repair
brain=claude rc=0 resolves=/home/.codex/skills  contents=[baked-a]
brain=codex  rc=0 resolves=                     contents=[]        <- symlink loop, exit 0
```

Boot now succeeds and the baked skills are silently unreachable. That is a strictly worse failure than `rc=1`.

**Concrete fix - both halves, tested.** Each brain asserts its own shape for `${DATA_DIR}/codex/skills`, because the two brains want that path to be a *different kind of object* (codex brain: a real directory; any other brain: a link out to the image).

In the codex-brain block, before `mkdir -p "${BRAIN_CRED_DIR}/skills"` (`:491`):
```sh
# A previous non-codex boot left this as a link to ${HOME}/.codex/skills; it
# must be a real dir here, or relinking ~/.codex below closes a symlink loop.
[ -L "${BRAIN_CRED_DIR}/skills" ] && rm -f "${BRAIN_CRED_DIR}/skills" || true
```
And section 3c becomes:
```sh
mkdir -p "${DATA_DIR}/codex"
chown "${APP_USER}:${APP_USER}" "${DATA_DIR}/codex"
if [ "${ENTRYPOINT_ENGINE}" != "codex" ]; then
  rm -rf "${DATA_DIR}/codex/skills"
  ln -sT "${HOME}/.codex/skills" "${DATA_DIR}/codex/skills"
fi
export CODEX_HOME="${DATA_DIR}/codex"
```
(`rm -rf` on a symlink removes the link, not its target.)

Tested across four sequences, with a tool-installed skill (`gstack-browse`) present in the image's `~/.codex/skills` alongside a baked one:

```
-- claude codex claude codex
brain=claude rc=0 resolves=/home/.codex/skills  contents=[baked-a gstack-browse]
brain=codex  rc=0 resolves=/data/codex/skills   contents=[baked-a]
brain=claude rc=0 resolves=/home/.codex/skills  contents=[baked-a gstack-browse]
brain=codex  rc=0 resolves=/data/codex/skills   contents=[baked-a]
-- codex claude codex claude   : same, mirrored
-- claude claude / codex codex : idempotent
```

### F2 - blocker - The reverse switch (codex -> claude) silently hides every tool-installed codex skill

**Claim (established finding 3, accepted as given):** "The reverse order (codex then claude) is fine."

That is true for the exit code only. It is false for correctness, and the spec's own recommended shape has the bug.

**What I ran.** The same harness, with the image home carrying both a baked skill and a `tool_library`-installed one (`~/.codex/skills/gstack-browse -> /opt/gstack`, which is how the gstack catalog entry installs its `gstack-*` skills):

```
### E. codex-then-claude, with the spec's [ -e ] guard
brain=codex  rc=0  $CODEX_HOME/skills contents=[baked-a]
brain=claude rc=0  $CODEX_HOME/skills contents=[baked-a]              <- gstack-browse GONE

### F. claude only, never a codex brain (baseline)
brain=claude rc=0  $CODEX_HOME/skills contents=[baked-a gstack-browse]
```

**Why.** The codex boot leaves `/data/codex/skills` as a real directory on the volume. On the next claude boot, 3c's `[ -e ]` guard is satisfied by that leftover directory, so the link to `${HOME}/.codex/skills` is never created, and `$CODEX_HOME/skills` resolves to the stale volume directory - which only ever held links into `/opt/bobi/skills`. Exit 0, no log line, codex-as-a-tool just stops seeing the skills the image installed for it.

**Fix.** The F1 fix above closes this too (the `if ENTRYPOINT_ENGINE != codex` branch replaces the leftover directory unconditionally). Sequence `codex claude codex claude` above shows `gstack-browse` restored on every claude boot.

**This also answers "does any OTHER state on the volume have the same hazard".** I checked every object the change puts under `/data/codex`:

| Object | Brain-switch hazard |
|---|---|
| `skills` | **Yes** - F1 (forward) and F2 (reverse). Both fixed above. |
| `auth.json` | No *new* hazard from the switch itself (both brains want codex OAuth for the same account), but see **F3** - an api_key-mode boot clobbers it. |
| `config.toml` | No. `bobi/brain/codex.py:387` is the only writer and it is brain-gated. |
| `AGENTS.md` | Minor, see **F8**. `_all_brain_targets()` is *not* brain-gated. |
| PATH-alias helper binaries | No. Re-dropped per invocation; `chown` in 3c covers ownership, and I confirmed no root-run `codex` invocation exists in the entrypoint. |

### F3 - blocker - The `:547` edit points `materialize_codex_api_key_auth` at the durable volume, so an api_key-mode boot overwrites the subscription credential the feature just created

**Claim (§3.4, follow-on edit 1):** "`docker/docker-entrypoint.sh:547` - `materialize_codex_api_key_auth "${HOME}/.codex"` -> `"${CODEX_HOME}"`." Presented as a mechanical consequence of the export.

**What I read.** `docker/docker-entrypoint.sh:538-551` and `materialize_codex_api_key_auth` at `:321-330`:

```
321|   [ -n "${OPENAI_API_KEY:-}" ] || return 0
322|   log "Writing Codex API-key auth file from OPENAI_API_KEY"
330| path.write_text(json.dumps({"OPENAI_API_KEY": os.environ["OPENAI_API_KEY"]}) + "\n")
538| if [ "${BOBI_AUTH:-api_key}" != "subscription" ]; then
546|   else
547|     materialize_codex_api_key_auth "${HOME}/.codex"
```

Today `:547` writes to the container overlay - ephemeral, harmless. After the edit it writes `/data/codex/auth.json`. So on a **claude-brained team with `BOBI_AUTH=api_key` and `OPENAI_API_KEY` set**, every boot overwrites the codex *subscription* credential on the volume with an API-key file. `run_bootstrap` at `:635-639` then refuses to re-mint it (`OPENAI_API_KEY is set; it overrides subscription auth`), so the team is wedged with no path back. Silent on-disk credential destruction plus a refusal to recover.

This is exactly the "latent for eng-team, fail-closed for the next team" argument the spec itself uses to justify pulling `tool.yaml` (F12) into scope - applied to a hazard it creates. It does not bite this deployment (`BOBI_AUTH=subscription`, `OPENAI_API_KEY` unset, so `:538` skips the whole block), which is why it reads as mechanical.

**Fix.** Leave `:547` pointing at `${HOME}/.codex`. The api-key materialization is deliberately a *non-durable* convenience for a non-codex brain; redirecting it to the volume gives it authority it was never meant to have. If the intent is that an api_key-mode claude team should get durable codex api-key auth, that is a separate decision and needs to say what happens when both credentials exist. Either way the spec must state the interaction, and the `elif [ -n "${OPENAI_API_KEY:-}" ]` log at `:549-550` is the model to copy.

### F4 - major - The shadow-env refusal is a brain-credential invariant applied to a tool target, and the spec is silent on it

(This is the brief's extra Job-3 item. **Verdict: defect, not correct-and-should-be-stated.**)

**What I read.** `bobi/auth_bootstrap.py:635-639` raises when `os.environ.get(spec.shadow_env)` is set. With `target="codex"`, `spec.shadow_env` is `OPENAI_API_KEY` (`:107`). And `tests/test_auth_bootstrap.py:1220-1227` pins exactly the state change 2 creates:

```python
def test_run_bootstrap_codex_refuses_with_openai_key(slack_config, monkeypatch):
    monkeypatch.setenv(BRAIN_ENV, "codex")
    monkeypatch.setenv("OPENAI_API_KEY", "sk-openai-x")
    with pytest.raises(RuntimeError, match="OPENAI_API_KEY"):
```

`login-bootstrap codex` on a claude brain sets `os.environ[BRAIN_ENV] = "codex"` - the same state - so a team with `OPENAI_API_KEY` in its runtime env cannot log codex in by subscription.

**Why it is a defect, not just undocumented.** The entrypoint states the premise is false for codex: `:535-536`, "Unlike Claude, Codex does not read OPENAI_API_KEY directly; it expects `~/.codex/auth.json`." So an ambient `OPENAI_API_KEY` does **not** shadow a codex OAuth credential on disk the way `ANTHROPIC_API_KEY` shadows Claude's. The refusal is a Claude-shaped invariant copied onto a spec where it does not hold, and it is a real exclusion: `OPENAI_API_KEY` is a legitimate env var for other tooling on a claude-brained team.

**Fix - and it simplifies the spec.** §3.3 already scopes the gateway guard (`:613-624`) to `target is None` as a one-off "small edge". Both guards are arguments about the *brain's* credential path. Scope **both** to `target is None` and the spec gains one rule instead of one special case:

```python
if target is None:
    ... gateway guard (:613-624) ...
    ... shadow-env guard (:635-639) ...
```
The existing test at `:1220` still passes (it drives `BRAIN_ENV` directly, so `target` is `None`). Then say in "Accepted and stated": a codex *tool* login is permitted alongside an ambient `OPENAI_API_KEY`, and the OAuth `auth.json` wins because codex reads only that file.

### F5 - major - Section 3c's placement is specified loosely enough to abort boot under `set -u`

**Claim (§3.4):** "New section 3c ... placed **after** the codex-brain block ends at `:532`."

The two follow-on edits consume `${CODEX_HOME}`: `:547` and `:557`. Both sit at `:538-563`. An implementer who satisfies "after `:532`" by placing 3c after the subscription sweep at `:563` - also literally after `:532`, and a natural reading given 3c is a new numbered section - leaves `${CODEX_HOME}` unset at `:547`/`:557`. With `set -euo pipefail` (`:14`) that is `CODEX_HOME: unbound variable` and an immediate boot abort on every machine.

The spec is emphatic that placement is load-bearing ("The placement and the guard are load-bearing", "Both are required, in writing, before anyone implements this") and then under-specifies it by one boundary.

**Fix.** State the interval, not the floor: "between `:532` and `:538`" - 3c must precede the api-key materialization block that reads `${CODEX_HOME}`.

### F6 - major - The on-demand trigger double-delivers the human's reply: the running manager receives it too

**Claim (§3.1, implicitly):** the waiter is `login-bootstrap`'s own process, and the brain's absence is irrelevant.

True at boot. For the *other* trigger - the director running `login-bootstrap codex` while the manager is live - I checked whether event delivery is fan-out or competing-consumers:

```
event-server/core/src/core.ts:1939  export async function admittedDeploymentIds(...): Promise<Set<string>>
                              :1958      for (const id of ids) admitted.add(id);
```
Fan-out: every subscriber indexed for the key is admitted. `login-bootstrap` registers on the workspace app topic (`auth_bootstrap.py:543-544`, topic `slack:{team}:app:{app}` from `_slack_topic` at `:278-283`), which is the same topic the manager subscribes to. And the adapter does emit the reply: a thread reply with no `@mention` becomes `slack.thread_reply` (`chat-sdk-slack.ts:121-122`).

So the human's "ready" message is delivered to **both** `login-bootstrap` and the director. The director will see an unexplained message in a thread and answer it. Not a feasibility blocker - the wait still works - but an unenumerated behaviour on the trigger the spec is actually adding, and it lands in the one channel Zach has previously called out for spam.

**Fix.** Either make the ask text tell the human that a stray reply from the director is expected, or add a line to the §3.5(b) prompt text telling the director to ignore threads rooted on a `bobi subscription login` message. One sentence; it just has to be a decision rather than a surprise.

### F7 - major - Q1 Option A (block indefinitely at boot) has no watchdog above it, and the spec's Q1 does not weigh that

**Claim (§5, Q1):** "**Option A (recommended): split by trigger.** At boot, block indefinitely on the ask ... an indefinite block leaves exactly **one** ask in Slack instead of one per restart."

The restart-loop cost is stated; the indefinite-block cost is not. `login-bootstrap` runs at `:575`, inside section 4. The supervisor sidecar - the thing that "watches the director's progress from OUTSIDE (health endpoint + process table + status-file freshness)" and "restarts a wedged director from below" - is not started until section 5 (`:590-640`, `exec` at `:637`/`:639`). So under Option A a credential-less machine blocks forever in section 4 with **nothing watching it**: no health endpoint, no status file, no process to restart, and no second ask. Today's restart loop is at least visible in `fly logs` and self-heals if the credential arrives by another route.

Option B's cost (Slack spam) is a nuisance; Option A's cost is an indefinitely silent machine. Neither is obviously right, and Q1 currently presents only one side of each.

**Fix.** Q1 should put the watchdog gap in front of Zach, and offer the shape that has neither cost: block at boot with a long but finite timeout (hours, not 600s), and on timeout re-post *into the existing thread* rather than posting a fresh ask. One ask in Slack, and the machine still cycles and stays observable.

### F10 - minor - §3.2(d)'s justification for thread-scoping is wrong, and verification item 4 cannot be written as described

**Claim (§3.2(d)):** "Without a thread anchor, unrelated chatter in `#bobi-eng-team` would read as 'ready'."

The adapter drops exactly that. `chat-sdk-slack.ts:114-125`: a channel `message` with no self-mention and no `thread_ts` falls through to `else { return { event: null }; }`. Plain channel chatter is never delivered, so it cannot read as ready.

The real exposure is narrower and different: an unrelated **thread reply** elsewhere in the channel (`:121-122` -> `slack.thread_reply`) or any `@mention` of the bot in the channel (`:115-116` -> `slack.mention`). Both carry `fields.channel` equal to the login channel and both pass today's filter.

This matters because **verification item 4** is written against the wrong event shape: "A message in the login channel with no/other `thread_ts` is ignored." The "no `thread_ts`" half cannot be written as a real event - the adapter never emits one. Half the test is unreachable.

**Fix.** Restate the justification as "an unrelated thread reply or a bot @mention elsewhere in the channel", and narrow item 4 to "a human `slack.thread_reply` carrying a *different* `thread_ts` is ignored".

### F11 - minor - The spec does not say which field carries the thread anchor, and on the only path this deployment uses, the obvious choice is a no-op

**Claim (§3.2(d)):** "The adapter sets `fields.thread_ts` (`:166`) and builds a thread-anchored `conversation` (`:173`)." Both are true; the spec then does not say which one the filter reads.

It has to be `fields.thread_ts`. On the legacy Slack channel-name path - `BOBI_LOGIN_CHANNEL=#bobi-eng-team`, which Appendix A records as this deployment's live value - `_extract_code` sets `expected_conversation = ""` (`:477` for the `str` form, `:481-483` for the resolved `LoginChannel`), and `_conversation_matches` returns `True` unconditionally on an empty expectation:

```
440| def _conversation_matches(expected: str, actual: object, source: str) -> bool:
441|     if not expected:
442|         return True
```

So an implementation that thread-scopes by comparing the inbound `conversation` ref would be a **silent no-op on the only path in production**, and would pass a gateway-path unit test while doing nothing live. The `conversation` ref is usable for *replying*; it is not usable as the filter on this path.

**Fix.** §3.2(d) should name the field: the predicate matches `fields.thread_ts == <ask ts>`. And `_wait_for_reply`'s return value - which §3.2(c) says is "the inbound event's `conversation` ref" - needs a stated fallback for the legacy path, where the thread to post into is `(legacy_slack_channel, thread_ts)`, not a ref.

### F12 - minor - Q3's `file_lock(blocking=...)` is unwarranted: it adds a second mechanism for an invariant Q2 already assigns to the director

**Claim (§5, Q3):** "Recommended: enforce it in code with a non-blocking lock per target ... add `blocking: bool = True` to `file_lock` and pass `LOCK_NB` when false (4 lines there, 3 in `auth_bootstrap`), keeping one locking code path in the tree."

Three reasons not to:

1. **Q2 already recommends director-only**, and says so for exactly this reason: "It keeps one pending ask per tool naturally (one director, one dedup point)." Adding the lock gives the invariant two enforcers. If the policy holds, the lock is dead code; if it does not, the policy line is wrong and should be fixed.
2. **`run_bootstrap` already short-circuits.** `:630-633` returns `True` immediately when the credential exists, re-read after the `BRAIN_ENV` override at `:626-627`, so it is target-aware for free. A second `login-bootstrap codex` *after* the first succeeds is already a clean no-op.
3. **The residual race is cosmetic.** The only uncovered window is two asks posted before either completes - duplicate Slack messages, not a wrong credential or a corrupt file. Spending a change to a shared primitive (`bobi/fsutil.py:162`, every caller's semantics) on message tidiness inverts the cost.

**Fix.** Take Q3's own fallback: prompt-only policy, race documented. Leave `file_lock` alone. If dedup later proves necessary, the cheap local shape is a pidfile in the agent's run dir, not a new mode on a tree-wide primitive.

### F15 - minor - Verification gaps

Beyond items 4 and 7 (F9, F10), four assertions that should exist and do not:

1. **The brain-switch sequence.** Item 13 tests "codex brain boots clean" - a single brain. F1 and F2 are switch bugs and neither is pinned. Needed: claude -> codex -> claude on one `/data`, asserting `rc=0` and that `readlink -f $CODEX_HOME/skills` resolves and lists both a baked and a tool-installed skill on each claude boot. My harness is the shape; it does not need docker.

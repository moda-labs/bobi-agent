# OAuth sign-in for remote MCP servers

> **Status:** Approved
> **Tracking issue:** moda-labs/bobi-agent#1155 · **Created:** 2026-11-09 · **Last amended:** — (see Amendments)
>
> Markers: `[ ]` idle · `[wip]` in progress · `[x]` done · `[f]` failed/blocked (always with a note)

## Purpose

A headless team can use any OAuth-only remote MCP server that supports device-code sign-in by adding `auth: oauth` to its `mcp_servers` entry.
Bobi signs in once through a device-code link posted to the team's login channel, keeps the grant on the volume, and refreshes tokens forever after.
Driving case: Zesture's MCP (`https://app.zesture.ai/mcp`) on the baohua team (moda-agents).

## Problem

- Remote MCP auth today is a static `headers:` value, interpolated from `${VAR}` once per `Config.load()` (`bobi/config.py:270-284`, stored at `bobi/config.py:724`).
- OAuth MCPs issue short-lived tokens.
  Verified live 2026-11-09 against Zesture's AuthKit (`https://plucky-willow-54.authkit.app`):
  - device-code sign-in works with a dynamically registered public client (`token_endpoint_auth_method: none`), `resource=https://app.zesture.ai/mcp`;
  - access token `expires_in: 300`, `aud` = the resource, accepted by Zesture's MCP (`initialize` → 200);
  - refresh succeeds and **rotates** the refresh token (the old one was still accepted seconds later — a grace window, not reuse).
- Headers are frozen for a session's life.
  The manager loads config once at boot (`bobi/service.py:514`, passed at `:737`); a `Session` reuses `self._extra_options` for boot, rotation, and recovery (`bobi/session.py:357-359`, `:495-511`); workflow runs load config once for all steps (`bobi/workflow/orchestrator.py:685`, `:785`).
  A token injected at session start is dead within 5 minutes.
- No MCP OAuth exists in bobi.
  `bobi/setup/mcp_registry.py:15-17` and the Sentry `oauth_note` claim "the SDK authorizes them at first connect"; nothing implements it (Sentry also has no device endpoint).
  The setup web UI says the opposite (`bobi/setup/webui/server.py:901-902`, `bobi/setup/webui/static/app.js:2057`).
- MCP preflight failures are fatal on every path: `_judge_mcp_server` (`bobi/validate.py:704-727`), plus the whole-probe timeout/exception path and the missing-from-status path (`bobi/validate.py:684-713`) all return `required=True`; `_validate_or_raise` raises (`bobi/service.py:518`), the CLI exits 1, the supervisor crash-loops.

## Solution

**Config.** `mcp_servers.<name>.auth: oauth` on a `type: http`, `https://` entry.
`Config` only validates (parse stays pure; `build_render` parses compose temp dirs at `bobi/build_render.py:261,285`).
Optional `oauth_identity: <email>` pins the identity allowed to sign in (checked on every sign-in, including the first and `--rebind`).
Rejected at load: non-`http` type, non-https URL, an `Authorization` header alongside, a name not matching `^[a-z0-9_-]+$`.
No loopback or http exemption in product code; tests run the fake AS + fake MCP over TLS with a per-session self-signed cert trusted via `SSL_CERT_FILE`.

**Grant** (`bobi/mcp_oauth/`).

- Discovery: RFC 9728 resource metadata from the 401's `WWW-Authenticate` `resource_metadata`, else the path-inserted well-known URL; its `resource` must equal the configured URL exactly.
  AS metadata from RFC 8414 path insertion on the chosen `authorization_servers[i]`, then the OIDC `openid-configuration` fallback; its `issuer` must exactly equal that `authorization_servers[i]` (RFC 8414 §3.3; issuers with paths are fine).
  HTTPS only; `follow_redirects=False` on every OAuth and proxied call.
  Requires `device_authorization_endpoint` + `registration_endpoint`, else a clear error naming the missing capability.
- Dynamic client registration once (public client, client name `bobi <instance>`, grants `device_code` + `refresh_token`).
- Device flow with `resource` = server URL, scopes `openid email offline_access` ∩ `scopes_supported` (all three when `scopes_supported` is absent).
- Every sign-in: require an `id_token` (none → refuse with a clear error); check `iss` = pinned issuer and `aud` contains the client_id (no signature check — TLS from the pinned token endpoint suffices, OIDC Core §3.1.3.7(6)); if `oauth_identity` is set, `email` must match or the grant is not stored.
  Pin `sub`; a later sign-in with a different `sub` is refused unless `mcp-login --rebind`.
  `sub` pinning stops a wrong human on a re-ask, not a same-uid role (which can run `--rebind`); `oauth_identity` is the guard that holds against both.
- Grant store `run/state/mcp-oauth/<name>.json`: 0600 on every write (including rotations), atomic replace, refuses symlinks, `fcntl` lock.
  Holds `resource` (the **only** upstream URL the proxy will ever use), issuer, pinned `token_endpoint` + `device_authorization_endpoint`, client_id, `sub`/email, refresh token, access token, expiry, a generation counter.
  Refresh never re-discovers.
  A configured URL differing from `grant.resource` = unsigned, and the ask names the mismatch.
- Refresh: under the lock, re-read the file, adopt a newer refresh token if present, refresh against the pinned endpoint, persist the rotated token **before** using the new access token.
  `invalid_grant` marks the grant lapsed only if the generation is unchanged.
- No token or header value is ever logged: token fields are `repr=False`, token-endpoint bodies are never logged, `httpx`/`httpcore` loggers held at WARNING inside the module.

**Proxy** (in the manager process).

- Started inside `run_manager_from_config` under the manager instance lock (`bobi/service.py:559-566`), so a second `bobi start` never touches it.
- Port + local secret persist in `run/state/mcp-oauth/proxy.json` (0600) and are reused across boots; a new port only if the old one cannot be bound.
  Surviving children (detached subagents, `bobi/subagent.py:1048`; supervisor leaves them, `bobi/supervisor/supervision.py:352-358`) keep working across a manager restart.
- Routes exactly `POST|GET|DELETE /mcp/<name>`; everything else (suffixes, `..`, unknown names, `/.well-known/*`) → 404.
- Checks the local secret with `hmac.compare_digest`; a wrong or missing secret → 403, no `WWW-Authenticate`.
- Request headers forwarded: allowlist `Content-Type`, `Accept`, `Mcp-Session-Id`, `Mcp-Protocol-Version`, `Last-Event-ID`; `Authorization` set to the upstream token.
  Response headers returned: allowlist `Content-Type`, `Mcp-Session-Id`, `Cache-Control`. Streams responses (SSE).
- Upstream 401, or 403 carrying `WWW-Authenticate` → refresh once → replay the buffered request (body cap 1 MiB); still failing → the 503 path.
- **Never** returns a 401 or `WWW-Authenticate` to the brain (inference: either could start Claude Code's own OAuth or step-up).
  Unsigned/lapsed, or refresh-and-replay failed → HTTP 503 with body `{"jsonrpc":"2.0","id":<request id or null>,"error":{"code":-32001,"message":"<name> MCP is not signed in. A human must complete sign-in in the login channel. Do not attempt sign-in yourself."}}`, and no upstream call.
  The body never names the CLI (an agent with a shell must not be nudged into minting codes).

**Session wiring — one resolver.**
`mcp_oauth.resolve_servers(mcp_servers, root)` is called in each brain's `make_session` (`bobi/brain/claude.py:913`, `bobi/brain/codex.py:509`, `bobi/brain/stub.py:252`) with `root = paths.bound_root()` (`bobi/paths.py:52`); `_async_probe_mcp` pre-resolves against its explicit `project_path`.
It **returns a new dict and never mutates its input** (the same `cfg.mcp_servers` is shared by `Session._extra_options`, the orchestrator, and `run_persistent_agent`), and is idempotent (entries without `auth` pass through).
Each `auth: oauth` entry becomes `{type: http, url: http://127.0.0.1:<port>/mcp/<name>, headers: {Authorization: Bearer <local secret>}}` from `proxy.json`.
If `proxy.json` is absent, the server is omitted — the upstream URL is never passed to a brain.
If `root` is `None` (webapp `spawn_team`, setup UI), Codex's `make_session` skips the `config.toml` write entirely, so an unbound process never strips a declared OAuth server from the host-shared file.
Every boot, rotation, recovery, workflow step, and preflight session re-reads `proxy.json`.

**Preflight.**
OAuth servers are not judged by the probe: `_check_mcp_servers` never adds OAuth names to `probe_names` (`bobi/validate.py:666`), but keeps them (resolved) in the server dict the probe session gets — dropping them would make `bobi doctor` / a second `bobi start` on a live Codex team rewrite the shared `config.toml` without them.
The probe's timeout/exception/missing paths (`bobi/validate.py:679-713`) only ever see `probe_names`, so they cannot block on an OAuth server.
OAuth servers get a grant-store judgment — signed / unsigned / lapsed — always `required=False`.
Non-OAuth servers keep today's blocking behavior.
This also makes `spawn_team`'s parent-process preflight (`bobi/service.py:386-392`) correct without a proxy.

**Sign-in ask** — one daemon thread per OAuth server, in the manager, never on a session event loop.

- Reuses auth_bootstrap's channel and listener machinery through new **keyword parameters with defaults** — subscription login behavior and every name/signature `tests/test_auth_bootstrap.py` patches stay unchanged:
  `require_thread=True` threaded through `_ready_reply` / `_anchor_matches` / `_ask_text` / catch-up recovery (today a `D…` DM is threadless and any DM message counts, `bobi/auth_bootstrap.py:575-576,670-671`); an ask-state path override; ask-text and kind parameters in place of the `SubscriptionLogin` spec.
  Kind `mcp:<name>`; ask-state at `run/state/mcp-oauth/<name>.ask.json`; listener name `login-bootstrap-mcp-<name>-<pid>`.
- Ask text (exact): "`<name>` MCP needs sign-in (signs in at `<AS host>`, client `bobi <instance>`). Reply **in this thread** when ready; codes are only ever posted in this thread right after your reply. `mcp:<name>` — {_ASK_MARKER}" so restart recovery (which matches the marker + kind, `bobi/auth_bootstrap.py:1082`) finds it.
- Only an in-thread human reply counts.
  **Inbox filter:** `bobi/events/drain.py` `drain_loop`, ahead of `reactor.process`, drops any chat event whose source, conversation, and `fields.thread_ts` match a live MCP ask anchor (in-process registry filled by the sign-in thread after posting, cleared with the ask state); a dropped event still completes its batch ack.
- On the reply: device flow → post `verification_uri` (https required) + user code in-thread → poll → store → post "signed in as `<email>`".
  `expired_token` → post "code expired, reply again" and keep waiting.
- A lapse posts once per lapse: "`<name>` sign-in lapsed. If you did not revoke it, the token may have been stolen — revoke the bobi client in the provider."

**Sign-in thread loop** (one per OAuth server; always runs; never exits on error):

- Signed → poll the grant file every 10s for a lapse (the proxy writes lapses there; same process, no other channel).
- Unsigned/lapsed → connect the listener **first** (failure or `wait_connected()` False → warn, back off 30s doubling to 10m, retry; never post before the listener is live), post or re-attach the ask, then wait in ≤30s slices, re-checking the grant generation between slices.
- Any generation increase (thread or `mcp-login`) → cancel the pending ask and send the reconnect sentinel.
- `$BOBI_LOGIN_CHANNEL` unset → no ask or lapse posts, warning logged; the loop still watches the grant so an `mcp-login` is picked up.

**Pick-up (manager only).** After any sign-in, the thread sends an MCP-reconnect sentinel to the manager inbox (pattern: `COMPACT_SENTINEL`, `bobi/session.py:1314`); it is acted on in `waiting_input`, and a sentinel dropped in another state is covered because any later session build re-resolves.
Child sessions (subagents, workflow steps) started while unsigned pick the server up at their next session build; documented in `docs/MCP_OAUTH.md` failure modes.
At idle the session calls a new optional brain-session method `reconnect_mcp(name)`: Claude → SDK `reconnect_mcp_server(name)`; Codex → no-op (it renders config per session and re-reads `config.toml` per turn, `bobi/brain/codex.py:532`).
No session rebuild; the transcript is untouched.
Raise the `claude-agent-sdk` floor to a version with `reconnect_mcp_server` (verified present in 0.2.101+; 0.2.87 unverified).

**CLI.** `bobi agent <name> mcp-login <server> [--rebind]`, registered alongside `login-bootstrap` in the `agent` group (`bobi/cli.py:4888-4910`); run as the app user (`docker/docker-entrypoint.sh:627` `as_app` pattern).

**Accepted risk** (written into `docs/SECURITY.md` following the OTLP-credential precedent at L245-255): every role runs as the agent user with shell (`docs/SECURITY.md:225-233`), so any role — including a prompt-injected one — can read the grant file and exfiltrate a long-lived refresh token for the signed-in identity.
The design limits blast radius (narrow scopes, `oauth_identity`, theft-aware lapse message, revocable per-client grant) but cannot prevent it in a single-uid container.
This is the same class as existing env secrets (e.g. baohua's Google Ads refresh token).

**Alternatives rejected.**

- Inject a fresh header at `make_session` only: tokens die in 5 min; sessions live for days.
- Claude Code's native MCP OAuth / `headersHelper`: browser loopback redirect (headless-unusable) or unverified headless trust gating; Claude-only; baohua pins CLI 2.1.284.
- Per-vendor API keys: not ours to add for third-party MCPs.
- Rebuild the manager session to pick up a server: every mid-session rebuild today starts fresh (`bobi/session.py:580,785,1368`); `reconnect_mcp_server` is simpler.
